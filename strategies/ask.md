# 动作手册 · ASK（提问）

> 本文件是 V0.3 不确定性消解引擎的**动作手册**之一，只处理 **ASK**。
> 类型判据、动作定义、优先级与组合规则一律以 `core/uncertainty-classifier.md`（下称**契约**）为准；本文件不发明第六种类型或第六种动作。
> 所有「用户可见模板」遵守 `SKILL.md` §2.1（对外表达规范）：不出现机制词、章节号、工具名。

---

## 适用对象

**对应类型：Type A（Known Unknown）—— 只有 Type A 用 ASK。**

| 项 | 内容（契约 §2 判据） |
|---|---|
| 判据 | 用户**明确提出**一个待定项，或**承认**某个决定还没做 |
| 典型原话 | "数据库选 MySQL 还是 PostgreSQL？""这个我还没定""你帮我定也行，但我倾向…" |
| 一句话 | 用户知道有这个岔路口，只是还没选 |

**不适用（命中任一即换动作）**：

- 用户已明确说清且无冲突 → Type D → **不动作**，直接进规划/组装
- 答案客观存在于可读环境（配置、依赖清单、git history、既有产物）→ Type E → **INSPECT**（契约 R1）
- 用户用形容词/感受/参照物表达目标 → Type B → **SHOW**（契约 R2）
- 用户未意识到该缺口存在 → Type C → **TEACH**（契约 R3）
- 当前无法确认、须由真实执行结果回答 → **DISCOVER**（契约 §4 Step 6）

---

## 前置条件

**以下任一成立时，本动作不得使用：**

1. **能查到的不能问**：答案在可读环境里 → 转 INSPECT，不得包装成问题问用户（契约 R1）。
2. **形容词类缺口不能追问**：用户给的是感受/参照物 → 转 SHOW，且同轮内不得出现"你所说的 X 具体是指什么"（R2）。
3. **认知未补齐不能问**：命中 Type C 时不得跳过 TEACH 直接问用户答不出的问题（R3）。
4. **同轮额度与顺序**：一轮最多 1 个 TEACH 块 + 1 组 SHOW + 1 组 ASK（≤3 题），不得全量铺开。同轮内有多个动作时，顺序依动作优先级、不依决策树 Step 序：`INSPECT → SHOW → TEACH → ASK`；**TEACH 恒先于 ASK**（用户不知道有这个缺口时先教再问，否则用户是在信息不全时作答）；**SHOW 与 ASK 同轮时，SHOW 的结果必须先处理完才能展开 ASK**；同一缺口内不得对已 SHOW 的模糊词追加 ASK（契约 R4；`SKILL.md` §11.0 规则 6、规则 7）。
5. **只影响措辞的不问**：答案不改变方案结构的问题一律不问（`SKILL.md` §3 选取原则）。
6. **已答过的不问**：不得重复问，也不得换一种措辞追问同一个点（`SKILL.md` §6.4）。
7. **授权默认后不问**：用户说"随便 / 你决定 / 直接给"→ 不再为走完流程追问；非阻塞项取默认值并显式进「待确认假设」（`SKILL.md` §6.3）。
8. **同一缺口连续 2 次没解决**：非阻塞项停止追问、用默认 + 进假设区；阻塞项改为"输出可完成的部分 + 说明仍缺哪一个决定"（`SKILL.md` §3.2）。

> ASK 是优先级最低的动作（`D 不动作 > E→INSPECT > B→SHOW > C→TEACH > A→ASK > DISCOVER`）。落到 ASK 之前，先确认前四者都不成立。

## 执行步骤

1. **跑决策树，确认落在 Type A**（契约 §4 Step 1→4 逐条短路；正文精简版见 `SKILL.md` §2.5）。任何一步命中它类 → 立即改派动作，不进入本流程。**动作选择先于问题排序**（`SKILL.md` §11.0）：只有 Type A 才能轮到提问。
2. **内部盘点缺口**，按 `SKILL.md` §3 优先级梯级（P0 目标与产物 → P1 核心对象 → P2 硬约束 → P3 风格质感）分层。
3. **选问 ≤3 题**：同层用 `SKILL.md` §3 一级裁界（能排除更多下游分支者优先）；仍无法区分再用 §11.1；上游依赖优先按 §11.6（B 改变 A 的定义/选项集/判断标准时 B 先问）。
4. **合并提问**：仅当同时满足 §11.7 六项条件时才合并；命中任一"必须拆开"条件即拆开。**按实际子问题数计入 1～3 上限**，语言包装不能绕过上限。
5. **每题三件套**：
   - 一句**影响说明**（"这决定了…"），只说影响，不写推理链；
   - **2～4 个选项**，互斥、尽量正交、中立、覆盖最可能的真实选择；
   - **推荐默认值置首，并在选项名末尾加「（推荐）」**，推荐理由写进该项说明。推荐依据必须来自**用户已说过的信息**或**成本/风险事实**，**不得写"最新/最好/最流行"这类价值判断**（`SKILL.md` §11.4 中立性）。
6. **保留自由表达通道**：每题末尾一句"也可以直接用自己的话描述"；不把采访变成选择题。
7. **优先调用宿主原生结构化提问工具**：宿主有 `ask_user_question` 这类工具时必须**实际调用**，不得只在正文列 A/B/C，也不得说"请在弹窗中选择"来代替调用。参数按下方"工具参数映射"；宿主无此工具或调用失败，才降级为正文提问并允许自由作答。
8. **一次只推进一步**：工具发出后正文不重复同一组选项；依赖未答问题的下一组不提前发出（R4）。
9. **接收回答**：一句复述理解 → 更新决策记录（`事项 / 类型A / 动作 asked / 状态 / 依据 / 结果`，契约 §6；正文格式见 `SKILL.md` §6.6）。`动作 = asked` 时状态只能是 `待决定` 或 `用户已确认`；**AI 建议不得升级成用户已确认**。
10. **信息一变就重分类**：用户答出的事实其实可从环境读到 → 转 INSPECT；答出的是形容词 → 转 SHOW；暴露新缺口 → 立即重跑决策树（R9）。

## 用户可见模板

```
好，动手之前有两件事只有你能定，它们会直接影响后面怎么做：

1. 这套系统将来主要跑在哪？（这决定部署方式、备份和迁移成本）
   ① 一台固定服务器，长期开机（推荐）—— 改动最少，以后要搬也不难
   ② 云主机，按量付费
   ③ 先在自己电脑上跑，以后再搬
   —— 也可以直接用自己的话描述，选项只是帮你省事。

2. 数据要保留多久？（这决定存储方案和清理规则）
   ① 长期保留，只增不删（推荐）—— 先不删最安全，以后想加清理也不难
   ② 保留 3 个月，到期自动清理
   ③ 还没想好

你可以只回答现在最确定的那一项，其余先跳过；也可以直接说"你决定"，我就按推荐值走，
并把每一处我自己定的地方都标在最后那份「待确认假设」里。
```

> **工具参数映射（非用户可见，仅内部执行用）**
> 宿主提供原生结构化提问工具（如 DSH 的 `ask_user_question`）时，上面这组内容**必须实际调用工具发出**。
> - `header`：≤12 字短标签（如"部署方式""数据保留"）
> - `question`：完整问句，把取舍说清楚
> - `options`：对象数组 `label` + `description`；**推荐项放首位，且 `label` 末尾加「（推荐）」**，推荐理由写进 `description`
> - **禁止手写"其他 / Other"选项**：界面自带自由输入框，手写会出现重复项
> - 一题只放互斥选项；不互斥的取舍 → 拆成两题，或对该题开启多选（**字段名以宿主工具自身定义为准**，如 DSH 的 `ask_user_question` 用 `multi_select`）
> - 工具发出后正文不重复同一组选项；不提前发出依赖未答问题的下一组

## 失败/降级路径

| 失败信号 | 换什么动作 / 怎么收场 |
|---|---|
| 用户答"不知道 / 不确定" | 记一次 unresolved，吸收顺带给出的其他有效信息，继续处理当前最高优先级缺口（`SKILL.md` §3.2；契约 R8 未解决仍计数） |
| 答非所问 / 明显回避 | 同上，记 unresolved；**不得换措辞追问同一个点**（§6.4） |
| 同一缺口连续 2 次 unresolved（非阻塞） | 停止追问 → 采用合理默认值 → 显式写入「待确认假设」 |
| 同一缺口连续 2 次 unresolved（阻塞） | 不继续换措辞追问 → 输出目前可完成的部分 + 简洁说明仍缺哪一个决定 |
| "随便 / 你决定 / 按你想的来" | **授权默认**：不计 unresolved，立即进入可交付阶段；非阻塞项用默认值（可转 DISCOVER），**阻塞项仍须拍板**（契约 R6） |
| 用户说"别问了，直接给" | 立即停止追问；全部 AI 自定内容进「待确认假设」；若仍存在真阻塞项 → 部分稿 + 最小关键决定 |
| 回答暴露该缺口答案在环境里 | 停止提问 → 转 INSPECT（R9 发现即重分类） |
| 回答是形容词/参照物 | 转 SHOW（R2）；同轮不再追问 |
| 主交付物已经能做，只剩措辞问题 | 不再问，直接进组装（`SKILL.md` §6.1/§6.2） |
| 原生提问工具不可用或调用失败 | 简短说明限制 → 降级为正文提问（≤3 题，给选项 + 自由作答）；**不得虚构工具，也不得声称已完成并不存在的调用** |

## 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 手写"其他 / Other"选项 | 结构化提问界面已自带自由输入框，会重复 | 只给 2～4 个真实选项，不加"其他" |
| 正文重复一遍工具里已发出的选项 | 同一轮重复占额度、用户要答两遍 | 工具发出后正文只写一句衔接 |
| 一题里塞多个互不排斥的取舍 | 用户只能给半套答案，答案不可用 | 拆成两题，或对该题设多选 |
| 问答案在配置/依赖清单里的事实 | 用户还得替你查，浪费且降低信任（R1） | INSPECT 后直接给结论 |
| 对"高级感"追问"具体指什么" | Type B 用户会开始编造标准（R2） | 转 SHOW 给 3 个正交方向 |
| 问满 3 题凑数 | 采访疲劳，答案质量下降，违反"宁可少问" | 只问答案会改变方案结构的那几项 |
| 推荐项不置首 / 漏写「（推荐）」 / 不给依据 | 用户成本变高，无法"一键接受" | 推荐默认值置首 +「（推荐）」后缀 + 写明依据 |
| 用"最新/最好/更专业"当推荐理由 | 把 AI 偏好写成客观判断（§11.4 中立性） | 依据用户已说的信息或成本/风险事实 |
| 用户答不出就换一组名词再问 | 违反 §6.4，伪装成新问题 | 先降维问法（§11.2）；仍答不出按降级处理 |
| 把「AI 建议」在决策记录里写成"用户已确认" | 契约 §6 约束 6 明令禁止 | 只进「建议·待确认」或「待确认假设」 |
