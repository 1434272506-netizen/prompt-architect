# 动作手册 · TEACH（补认知）

> 本文件是 V0.3 不确定性消解引擎的**动作手册**之一，只处理 **TEACH**。
> 类型判据、动作定义、优先级与组合规则一律以 `core/uncertainty-classifier.md`（下称**契约**）为准；本文件不发明第六种类型或第六种动作。
> 所有「用户可见模板」遵守 `SKILL.md` §2.1（对外表达规范）：不出现机制词、章节号、工具名。

---

## 适用对象

**对应类型：Type C（Unknown Unknown）—— 用户不知道自己缺这个，一旦踩空会返工、出事，甚至不可逆。**

| 项 | 内容（契约 §2 判据） |
|---|---|
| 判据 | 用户**未意识到**该缺口存在；缺口一旦踩空会造成**返工、风险或不可逆后果** |
| 典型原话 | "我要做一个 AI 客服""做一个自动交易机器人""做个能自动处理订单的系统" |
| 一句话 | 他不是没想清楚，是**不知道要在这里想** |

**不适用（命中任一即换动作）**：

- 用户**已经知道**这个缺口、只是还没定 → Type A → **ASK**（"知道但没定"不等于"不知道"）
- 缺口无害、只影响措辞 → 不动作，最多在「待确认假设」里带一句
- 答案在可读环境里（既有规范、配置、历史记录）→ Type E → **INSPECT**
- 用户用形容词表达目标 → Type B → **SHOW**；与 C 混合时按决策树取主导类型，另一性质只作备注（R5）
- 须由真实执行结果回答、且不是阻塞项 → **DISCOVER**（契约 §4 Step 6）

---

## 前置条件

**以下任一成立时，本动作不得使用（或必须改做法）：**

1. **一次 ≤3 条**（硬边界）：候选超过 3 条时只讲**后果最重**的 3 条，其余记「暂不做」或留到后续轮次（契约 §3；R4 同轮最多 1 个 TEACH 块）。
2. **不制造焦虑、不要求用户立即回答**（硬边界）：TEACH 的目的是让他**知道**，不是让他现在交答案；不得用恐吓、倒计时、"很危险"式话术。
3. **不得跳过 TEACH 直接问**：命中 Type C 时，**先 TEACH 补齐认知，再决定该缺口的后续动作**；不得跳过直接问用户答不出的问题（R3）。同轮内同时存在多个动作时，顺序依动作优先级、**不依决策树 Step 序**：`INSPECT → SHOW → TEACH → ASK`，其中 **TEACH 恒先于 ASK**——用户未意识到的缺口必须先补齐认知，再问需要拍板的问题，否则用户是在信息不全的状态下作答（契约 R4；`SKILL.md` §11.0 规则 6）。
4. **TEACH 本身不改变任何需求状态**：它只追加认知，不能被当作"用户已确认"；后续动作另起一行记录（契约 §6 约束 4）。
5. **只讲后果与最低必要知识**：不写成教程、不作技术培训、不展开原理长文；讲到"能参与决定"为止。
6. **不得用 TEACH 绕过阻塞项**：目标/范围/权限/费用/数据用途/不可逆操作仍须用户当场拍板（R6），TEACH 只是让这个决定变得可做。
   - **高风险 C 与阻塞项重叠时（契约 §3.1 第 2 条 / R14）**：**同一轮内先 TEACH、紧接 ASK 该阻塞项**（≤1 题，依 R4 合规）；**不得**把阻塞项推后，**也不得**借并列夹带其他普通 P0 问题。本项为 R6 在前置场景下的**并列例外**，不是推翻 R6。
7. **不得对已知缺口重复教**：用户已经知道的，再教一遍是浪费时间（§6.4 精神：不重复已答/已知）。
8. **评估必须诚实**：区分"事实"与"常见做法"；不确定就说不确定，不用权威口吻掩盖信息缺口。

## 执行步骤

1. **确认 Type C**：同时满足两条——用户**未意识到**该缺口存在；缺口踩空会造成**返工 / 风险 / 不可逆后果**。缺任一条就不做。
2. **列候选遗漏项并排序**：按后果严重度排（返工 < 风险 < 不可逆），取前 **≤3** 条。
   常见隐藏缺口素材（按同一方法自建，不限于此）：

   > **"AI 客服"类**：① 它答错了谁负责、能不能转人工（不可逆：错误答复发出去收不回）；② 答案从哪儿来、谁负责更新知识库（返工：来源不更新→答错→重建）；③ 它能直接做哪些操作（查单没风险，**改地址/退款不可逆**）；④ 客户数据进不进来、存多久、谁能看（数据用途，属阻塞项）；⑤ 上线后谁盯着它（成本与人力）。
   > **"自动交易机器人"类**：① 谁有下单权限、单笔与总额上限（不可逆：真金白银）；② 异常行情怎么熔断、谁负责停机；③ 回测与实盘的差异谁承担（返工：策略上线即失效）；④ 失败/断网时的兜底行为（挂着不管还是自动平仓）；⑤ 日志与追责口径。

3. **每条写清三件事**（顺序固定）：**缺什么 → 后果是什么（返工 / 风险 / 不可逆，说清代价） → 最低必要知识（一两句）**。
4. **语气平实、剂量克制**：说明"你现在不用回答，我只是先把它摆出来"；不追问、不催促、不评价用户之前的设计。
5. **给一条可选的下步走向**（"如果你想，我可以顺带把它补进方案里"），**不预告内部流程、不列步骤表**。
6. **落痕**：决策记录写 `类型C / 动作 taught / 状态不变 / 依据 / 结果`（正文格式见 `SKILL.md` §6.6）；**TEACH 本身不改变需求状态**，用户表态后的后续动作另起一行（契约 §6 约束 4）。
7. **输出后立即重新分类**（R3、R9）：按决策树 Step 2–4 重跑——用户表态变成待定项 → **ASK**；属环境事实 → **INSPECT**；用户能判断方向 → **SHOW**；须执行结果回答且**非阻塞** → **DISCOVER**（阻塞项不可，R6）。
8. **用户补充信息后立即重跑决策树**，不得沿用旧分类（R9）。

## 用户可见模板

```
在动手之前，有三件事我想先摆出来——不是要你现在回答，只是这几个地方踩空了会比较麻烦：

1. 客户问到它答不上来的问题，谁来接手？
   如果完全没人接，错误答复一旦发出去就收不回来（对外的消息、给客户的承诺都属于这类）。
   常见做法是设一个"转人工"的出口，超出一段范围就交给真人。

2. 它的答案从哪儿来、谁来更新？
   知识库没人维护的话，过一阵它就会答错，那时候往往要返工重做一遍内容。

3. 它能不能直接改客户信息或退单？
   查订单没风险；改地址、退款这类操作是不可逆的，通常要么只给建议、由人确认后执行，
   要么给一个额度上限。

这三条你不需要现在决定。你说一句"想用哪种"，我就按你的想法接着往下理；
如果暂时不想管，我会按最常见、最保守的方式先放在方案里，并标出来以便你随时改。
```

> **内部说明（非用户可见）** —— 剂量示例（对"自动交易机器人"同理）：一次只讲 **权限上限 / 熔断停机 / 回测与实盘差异** 这类"不问就会出事"的点，**不讲**策略数学、不讲框架选型。

## 失败/降级路径

| 失败信号 | 换什么动作 / 怎么收场 |
|---|---|
| 用户回"这些我知道" | **立即停止 TEACH**；他知道但没定 = 待定项 → 转 **ASK**（挑影响最大的 1 项问） |
| 用户被吓到（"那还能做吗"） | **降低剂量**：只保留 1 条最关键的，并说明可以先做最小版本、其余分期；明确"不影响现在开工" |
| 用户说"你看着办 / 随便" | **授权默认**：非阻塞项取保守默认并进「待确认假设」；**阻塞项（权限/费用/数据用途/不可逆）仍须拍板**（R6、`SKILL.md` §6.3 例外） |
| 用户不回应、直接换话题 | **不重复 TEACH**（TEACH 不计数、不追踪未解决，R8 只统计 ASK 通道）；不视为同意；继续推进可做部分，把相关缺口按保守默认写进「待确认假设」 |
| 候选缺口超过 3 条 | 只讲后果最重的 3 条；其余标「暂不做」或留到下一轮，绝不一次铺开（R4） |
| 用户反问技术细节（超出"最低必要知识"） | 答一句影响层面即可，不展开教程；需要深入时说明"这块等方案定了再细说" |
| 用户表态后缺口性质变了 | 立即重跑决策树（R9）：转 ASK / SHOW / INSPECT / DISCOVER（阻塞项不可 DISCOVER，R6） |
| 发现之前讲的结论不准确或过度断言 | **立即更正**，并区分"这是事实"与"这是常见做法"；不用模糊话掩盖 |
| 用户说"别教我，直接给" | 按授权默认处理 → 保守默认 + 全部自定内容进「待确认假设」；阻塞项仍须一句最小澄清（`SKILL.md` §6.3 例外） |

## 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 一次列 8 条风险 | 违反 ≤3 硬边界，用户只会焦虑且记不住 | 按后果排序取前 3 条 |
| 只列风险不说后果 | 用户无法判断要不要管（契约 §3 硬边界：只讲后果与最低必要知识） | 每条写清"踩空会怎样、代价是什么" |
| 用恐吓话术逼用户立刻决定 | 违反"不制造焦虑、不要求立即回答" | 平实陈述 + "现在不用回答" |
| 跳过 TEACH 直接问用户答不出的问题 | 违反 R3，用户只能猜或敷衍 | 先补认知，再按 Step 2–4 重分类 |
| 把 TEACH 当成拿到了确认 | TEACH 不改变任何需求状态（契约 §6 约束 4） | 状态不变，后续动作另起一行 |
| 对用户已知的缺口再教一遍 | 浪费时间，且显得没在听（§6.4 精神） | 已知未定 → 直接 ASK |
| 讲成技术培训 | 超出"最低必要知识"，压过真正需要拍板的决定 | 讲到能参与决定为止 |
| 用 TEACH 把阻塞项推到"以后再说" | 阻塞项必须当场定（R6） | TEACH 后**同轮**转 ASK 明确拍板（高风险 C 前置场景见前置条件 6，§3.1 第 2 条） |
| 讲完不重分类 | 违反 R3/R9，后续动作会用错通道 | 输出后立刻按决策树 Step 2–4 重跑 |
