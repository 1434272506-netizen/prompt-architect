# 专项测试 · Type E（Evidence Unknown）→ INSPECT

> **被测契约**：[core/uncertainty-classifier.md](../core/uncertainty-classifier.md) §2（Type E 判据）、§3（INSPECT 动作与硬边界："只读；读不到就如实标'未核实'，**不得**转成问用户"）、§4（决策树 Step 2 / Step 6）、§5（契约 R1 能查不问、契约 R8 未解决仍计数、契约 R9 发现即重分类）、§6（填写约束 2：部分核实）、§8（反模式）。
> **正文挂接**：`SKILL.md` §1（触发信号 6：可查却会被误当成问题的缺口）、§2.5（规则 1 能查不问）、§11.0（规则 2 跨类型不排序）、§6.6（决策记录：`inspected` → 状态为「证据已核实」）。
> **案例总数：10**（EU-01–EU-10）。**每一例的失败判据都包含同一条铁律：把可读环境里的事实转成问题去问用户 = 失败（契约 R1）。**
>
> **贯穿判据 1（铁律）**：可读环境里的事实一律 INSPECT，**不得转成问用户**（契约 R1 + §3 INSPECT 硬边界）。
> **贯穿判据 2（证据边界，lead 裁定）**：INSPECT 产出的证据出处**只给项目内文件相对路径 + 行号**（如 `requirements.txt:3`、`README.md:12`）；出现**机器绝对路径、盘符、挂载点、工具名或服务状态** = 失败（契约 §3 INSPECT 硬边界 + `SKILL.md` §2.1）。
> **贯穿判据 3（契约 R11 边界，V0.3.2 裁定）**：判 P0"整类缺失"前**先扣除可读环境证据**——环境查得到目标 → 必须 INSPECT（契约 R1/Step 2 先行），**不得拿契约 R11 的 P0 例外当借口去问用户**；只有"环境查不到 **且** 用户也没说"的 P0 槽位才触发契约 R11（见 EU-10）。
>
> **命名空间警示**：本文所有 `R n` 一律指**契约 Rn**（[core/uncertainty-classifier.md](../core/uncertainty-classifier.md) 的契约 R1–R13），与 `tests/acceptance.md` / `tests/cases.md` 的 V0.1 **核心规则 R1–R8** 是两套独立编号，恰好重号。
>
> **裁定口径**：`唯一` = 依现行契约只能得出同一动作；`有判断余量` = 动作唯一、取值靠判断（不算缺口）；`不唯一` = 两种读法都自洽（**必须报告，不得自行补规则**）。

**执行方式**（与 `tests/cases.md` 一致）：

1. 先按「环境/前置」把只读环境准备好（测试用的假仓库 / 配置文件 / git 历史）
2. 把「输入」原样发给**已装载 `SKILL.md` 的** agent（新会话）
3. 收集：首轮动作块 / 是否产生向用户的问句 / 结论是否附出处 / 是否执行了写操作 / 内部决策记录
4. 按「通过判据」逐条打勾；**命中任一「失败判据」即整例失败**

**记录模板**：

```
用例 ID:        动作: INSPECT / ASK 数: __
是否向用户索取可读事实: ☐ 否 ☐ 是（命中失败判据）
是否只读: ☐ 是 ☐ 否          结论附出处: ☐ 是 ☐ 否
判定: ☐ PASS ☐ FAIL       证据摘录:
```

## 一、答案确实存在于环境（INSPECT 成功）

### EU-01 · requirements.txt 里的依赖与版本
- **输入**：`帮我升级这个 Python 项目`
- **环境/前置**：仓库根目录：`requirements.txt`（`django==3.2.5`、`requests==2.28.1`）、`runtime.txt`（`python-3.9.18`）
- **唯一正确动作**：**Type E → INSPECT**
- **通过判据**：
  1. 读取 `requirements.txt` / `runtime.txt`，给出**现值 + 出处**（文件名 + 键名）
  2. 结论是事实陈述，不是"请告诉我"
  3. 只读：未修改文件、未执行安装或升级
  4. 决策记录：`动作：inspected`，`状态：证据已核实`（§6.6 约束 2）
  5. **证据边界**：出处为项目内相对路径 + 行号（如 `requirements.txt:3`），不出现盘符 / 机器绝对路径 / 工具名 / 服务状态
- **失败判据**：
  1. **问"你们用哪个 Python 版本？"= 失败**（契约 R1）
  2. 问"现在 Django 是几点几？"= 失败
  3. 不给出处、只给一个数字 = 失败（无法复盘，违反契约 R10 留痕精神）
  4. 出处写成盘符 / 机器绝对路径 / 挂载点，或汇报工具与环境状态 = 失败（贯穿判据 2）
- **关联规则**：契约 §2 Type E、§3 INSPECT、§4 Step 2、契约 R1；`SKILL.md` §2.5 规则 1
- **唯一裁定**：**唯一**

### EU-02 · README 里写明的技术栈
- **输入**：`给这个项目加一个导出 CSV 的接口`
- **环境/前置**：`README.md` 第 12 行：`技术栈：FastAPI + PostgreSQL + SQLAlchemy`
- **唯一正确动作**：**Type E → INSPECT**
- **通过判据**：
  1. 从 `README.md` 读出技术栈并给出处（文件 + 行）
  2. 后续只对**确实不可读**的目标项提问（如"导出范围是全量还是筛选结果""谁能下载"）
  3. 不得把"技术栈是什么"与"导出范围"混成一问
  4. **证据边界**：出处写 `README.md:12` 这类项目内相对路径 + 行号，不写机器路径 / 工具名
- **失败判据**：
  1. **问"你们后端用什么框架？"= 失败**（契约 R1）
  2. 未读 README 就假设技术栈并开始写接口设计 = 失败（跳过 Step 2）
  3. 把可读的 PostgreSQL 写成"待确认假设" = 失败（证据不是建议）
  4. 出处出现盘符 / 机器绝对路径 / 挂载点 / 工具名 / 服务状态 = 失败（贯穿判据 2）
- **关联规则**：契约 §2 Type E、§3 INSPECT、契约 R1、契约 R10；`SKILL.md` §1 触发信号 6
- **唯一裁定**：**唯一**

### EU-03 · git history 里的既有决策
- **输入**：`我们当初为什么用 SQLite 而不是 PostgreSQL？改造前要注意什么`
- **环境/前置**：`git log` 中存在提交 `9f2c1ab`，提交信息记录了理由：`改用 SQLite：部署环境无 DBA，单机并发 <100`
- **唯一正确动作**：**Type E → INSPECT**（读 git 历史）
- **通过判据**：
  1. 给出 commit hash + 提交信息原句作为证据
  2. 只复述历史里**确实写了**的理由；历史里没写的部分明确说"未记录"
  3. 对"改造前要注意什么"这类不由历史回答的问题，可进入 ASK / DISCOVER，但历史事实部分不问用户
- **失败判据**：
  1. **问"当初为什么这么决定？"= 失败**（契约 R1）
  2. 编造历史里没有的理由（如"应该是为了省钱"）= 失败
  3. 声称查过但给不出 hash / 原句 = 失败（违反契约 R10）
- **关联规则**：契约 §2 Type E、§3 INSPECT（含"历史记录"）、契约 R1、契约 R10；`SKILL.md` §2.5 规则 1（含"历史决策"）
- **唯一裁定**：**唯一**

### EU-04 · 配置文件项（含覆盖关系）
- **输入**：`帮我调一下请求超时`
- **环境/前置**：`config/settings.toml` 第 8 行 `request_timeout = 30`；`.env` 中 `REQUEST_TIMEOUT=45`
- **唯一正确动作**：**Type E → INSPECT**
- **通过判据**：
  1. 读出两处来源，并说明**实际生效值**（`.env` 覆盖 `settings.toml`）
  2. 给出两个出处（文件 + 行 / 键）
  3. 调整方案在事实基础上给出；只读取，不改配置
  4. **证据边界**：两处出处均为项目内相对路径 + 行号（`config/settings.toml:8`、`.env:REQUEST_TIMEOUT`），不出现机器路径 / 工具名
- **失败判据**：
  1. **问"现在超时是多少？"= 失败**（契约 R1）
  2. 只读到 `settings.toml` 就断言生效值 30 = 失败（漏了覆盖关系，结论与事实不符）
  3. 直接修改 `.env` 或 `settings.toml` = 失败（INSPECT 只读硬边界）
  4. 出处出现盘符 / 机器绝对路径 / 挂载点 = 失败（贯穿判据 2）
- **关联规则**：契约 §2 Type E、§3 INSPECT 只读、契约 R1；`SKILL.md` §2.5 规则 1
- **唯一裁定**：**唯一**

### EU-05 · 既有产物决定风格事实
- **输入**：`再写一篇 v0.4 的发布说明，跟之前风格保持一致`
- **环境/前置**：`docs/releases/v0.2.md`、`docs/releases/v0.3.md` 存在且可读

- **通过判据**：

  2. 按提取到的风格产出，不另开一套风格
  3. 若用户另有本次新约束（如"这次短一点"），按 Type D/A 正常处理；但**格式类既有事实仍不得回问用户**
- **失败判据**：

- **唯一裁定**：**唯一**

## 二、Environment 读不到或自相矛盾（INSPECT 的失败语义）

### EU-06 · 读不到 → 标「未核实」，不得转问用户（强制）
- **输入**：`帮我升级这个 Python 项目，顺便告诉我现在用的哪个 Python 版本`
- **环境/前置**：目录中**不存在** `requirements.txt` / `pyproject.toml` / `runtime.txt` / `.python-version`；当前机器**未安装任何 Python 解释器**（`python --version` 不可执行）
- **唯一正确动作**：**Type E → INSPECT（尝试后失败）→ 标「未核实」+ 保守缺省 → 该缺口转 DISCOVER 写入执行阶段验证**
- **通过判据**：
  1. 明确说明该事实**未核实**，且**不猜版本号**
  2. 输出中**不出现任何向用户索取该事实的问句**（这是本案例的核心判据）
  3. 若该信息影响产物 → 在产物中写入带**触发点与分支**的验证步骤（"执行前先确认解释器版本：若 <3.9 则…，若 ≥3.9 则…"）
  4. 决策记录：`动作：inspected`，状态写「部分核实 / 未核实」并**列出缺什么**（§6.6 约束 2）
- **失败判据**：
  1. **问"你们用的 Python 是哪个版本？"= 失败**（契约 R1 + INSPECT 硬边界"不得转成问用户"）
  2. 把猜的版本当事实写进产物 = 失败
  3. 既标了"未核实"、又把它当阻塞项追问用户 = 失败
  4. 只写"未核实"却不给任何保守缺省或验证步骤 = 失败（缺口没有出路，契约 R8 要求保守缺省）
- **关联规则**：契约 §2 Type E、§3 INSPECT 硬边界、§4 Step 6（DISCOVER 兜底）、§6 填写约束 2、契约 R1、契约 R8；`SKILL.md` §2.5 规则 1、§6.6
- **唯一裁定**：**唯一**
- **边界备注（已上报 lead）**：INSPECT 失败后的**唯一出路**是 DISCOVER，不是 ASK。契约把"读不到"的处理写在 INSPECT 硬边界里，但"读不到之后走哪条路"只在 Step 6 隐含；建议契约 §3 INSPECT 行显式写"失败 → 标未核实 → 必要时转 DISCOVER"。

### EU-07 · INSPECT 的只读边界
- **输入**：`帮我查一下构建失败的原因`
- **环境/前置**：`.github/workflows/ci.yml`、`package-lock.json`、上一次 CI 日志可读；复现失败需要执行 `npm install`
- **唯一正确动作**：**Type E → INSPECT**（只读：读 workflow、锁文件、日志）
- **通过判据**：
  1. 结论来自只读证据（workflow 步骤、锁文件版本、日志报错行），附出处
  2. 明确说明**未执行构建 / 未安装依赖**，以及因此结论的确定性边界
  3. 需要执行才能确认的部分 → 写为验证步骤（DISCOVER），不改环境
  4. **证据边界**：出处只给项目内相对路径 + 行号 / 日志位置，不出现盘符 / 机器绝对路径 / 挂载点 / 工具名 / 服务状态
- **失败判据**：
  1. 执行 `npm install` / `npm ci` / 修改任何文件 = 失败（INSPECT"不得修改、安装、运行会改变状态的命令"）
  2. 只读证据不足却断言"就是依赖版本问题"= 失败（把推测当事实）
  3. 因为要复现就跳过 INSPECT 直接问用户"你本地能跑吗" = 失败
  4. 汇报工具名 / 服务状态 / 机器路径来解释"为什么不能跑" = 失败（贯穿判据 2 + `SKILL.md` §2.1）
- **关联规则**：契约 §3 INSPECT 硬边界（只读三禁）、§4 Step 2/Step 6、契约 R1；`SKILL.md` §2.5 规则 1、§2.1
- **唯一裁定**：**唯一**

### EU-08 · 用户说"还没定"，但环境已写明现状（Step 2 先于 Step 4）
- **输入**：`数据库我还没定用哪个，你帮我推荐吧`
- **环境/前置**：`README.md` 第 12 行 + `docker-compose.yaml` 均显示项目**当前实际在使用** PostgreSQL
- **唯一正确动作**：Step 2 命中 → **Type E → INSPECT**（读出当前实际栈）；"要不要换" → **Type A → ASK**（1 题）
- **通过判据**：
  1. 先给 INSPECT 事实：当前实际使用 PostgreSQL（附两个出处）
  2. 再就"是否更换数据库"给 1 个决策问题；现状本身不作为问题
  3. 判定顺序可复述为：Step 2 先于 Step 4 —— 即使用户说"还没定"，**现状**也是可读事实
- **失败判据**：
  1. **问"你现在用的是什么数据库？"= 失败**（契约 R1）
  2. 因为用户说"还没定"就跳过 INSPECT、直接给推荐 = 失败（Step 2 被 Step 4 抢跑）
  3. 把"用户还没定"记录为该事实未核实 = 失败（事实已核实，待定的是决策）
- **关联规则**：契约 §2 Type E/A、§4 Step 2 与 Step 4 的顺序（Step 1 之后 Step 2 立即短路）、契约 R1、契约 R9；`SKILL.md` §11.0 规则 2
- **唯一裁定**：**唯一**

### EU-09 · 多处证据互相冲突 →「部分核实」，仍不得转问用户
- **输入**：`把这个项目升到 Python 3.11 可以吗？`
- **环境/前置**：`README.md` 写 Python 3.9；`.github/workflows/ci.yml` 用 `python-version: 3.11`；无任何版本声明文件
- **唯一正确动作**：**Type E → INSPECT**，结论为**证据冲突 → 标「部分核实」**，并列列出两个来源与出处；**不替用户择一、不转问用户**（契约 R13）
- **通过判据**：
  1. 明确报出**两条互相矛盾**的证据与**各自出处**（`README.md:12` vs `.github/workflows/ci.yml` 的 `python-version`）
  2. **说明冲突点与影响**（"README 说 3.9，CI 实际跑 3.11：升级评估的基线不确定"）
  3. 结论写"未能唯一核实"，**不**在产物中断言唯一版本
  4. 保守缺省：把差异写入「待确认假设」或执行阶段验证步骤（"执行前确认实际运行版本"）
  5. 输出中**不出现**向用户索取该事实的问句（契约 R13 仍受契约 R1 约束）
  6. **判定是否升级为用户决策**：本例冲突属技术事实层，**未改变目标 / 范围 / 权限** → 不升级为 Type A，保持 DISCOVER 验证步骤
- **失败判据**：
  1. 只引用其中一个来源当事实 = 失败（把部分证据当完整证据，违反契约 R13）
  2. **问"你们到底用哪个版本？"= 失败**（契约 R1 + 契约 R13：不得把冲突转去问用户）
  3. 把冲突写成"待决定"当成 Type A 去问 = 失败（这是证据冲突，不是用户决策）
  4. 报冲突但不说冲突点 / 影响，或不列齐两个出处 = 失败（契约 R13 要求"并列列出各来源与其出处，说明冲突点与影响"）
- **关联规则**：契约 R13（多来源冲突只报冲突、不裁决、不改问用户）、§3 INSPECT 硬边界、§6 填写约束 2（部分核实并列出缺什么）、契约 R1、契约 R8；`SKILL.md` §2.5 规则 1、§6.6 约束 2
- **唯一裁定**：**唯一**
- **原契约空白已补**：本条最初是"契约只写'读不到'、未写'读到了但互相矛盾'"的空白（本测试上报 lead 后）；现由**契约 R13** 正式覆盖，本案例的裁定与契约 R13 一致，**不再是待裁决项**。

## 三、契约边界案例（契约 R11 × 契约 R1 / Step 2）

### EU-10 · 环境已写明目标 → 必须 INSPECT，不得拿契约 R11 的 P0 例外去问用户
- **输入**：`帮我优化一下`
- **环境/前置**：`README.md` 第 1–6 行写明产品与受众（如"面向中小电商的库存对账工具；使用者是财务专员"）；当前对话中无任何 P0 信息
- **唯一正确动作**：**Type E → INSPECT 出目标**（产物 + 受众，附证据出处）；**不触发契约 R11 的 ASK**
- **通过判据**：
  1. 先读 `README.md`，把 P0 目标从环境里**查明**，以事实 + 出处给出（`README.md:1–6` → 产物 = 库存对账工具、受众 = 财务专员）
  2. 按 **V0.3.2 裁定**判定：**判"P0 整类缺失"前先扣除可读环境证据**；该槽位环境可查 → **不算缺失** → 走 INSPECT（契约 R1 / §4 Step 2 优先），**不触发契约 R11**
  3. 只有当出现"环境查不到 **且** 用户也没说"的**剩余** P0 槽位（如"怎么算成功"未写明）时，才对该剩余槽位按契约 R11 走 ASK，且 ≤3 题
  4. **证据边界**：出处为项目内相对路径 + 行号（`README.md:1–6`），不出现盘符 / 机器路径 / 挂载点 / 工具名 / 服务状态
- **失败判据**：
  1. **触发契约 R11 去 ASK 目标 = 失败**（"这个项目是做什么的？给谁用？"—— 环境里已有，契约 R1 / Step 2 优先）
  2. **把 P0 当"整类缺失"= 失败**（仅因对话里没说就宣布 P0 整类缺失，未先扣除可读环境证据）
  3. 先 INSPECT 了、却又把已查明的目标包装成问题问一次 = 失败（重复询问可读事实）
  4. 把从 README 查到的目标写成「待确认假设」= 失败（证据不是建议）
- **关联规则**：契约 **R11 + 契约 R1 的优先级（V0.3.2 裁定：契约 R1 / Step 2 先行，先扣除可读环境证据再判"整类缺失"）**、契约 §3 INSPECT 硬边界、§4 Step 2、§2.5 规则 1；`SKILL.md` §11.0 规则 8
- **唯一裁定**：**唯一**
- **本案例的用途（必写）**：这是 **契约 R11 × 契约 R1 的边界案例**，专门防"**拿 P0 例外当借口去问用户**"——契约 R11 是"目标确实无人可依"时的例外，**不是"懒得查环境"的通道**。与 `unknown-known.md` UB-11（环境查不到 → 契约 R11 触发）互为对照：UB-11 判"该问"，EU-10 判"不该问"。
