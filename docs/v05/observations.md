## O-1 · 跨会话 / 跨任务的 identity 与持久化边界（**本阶段最关注**）

### 为什么现在就要问

V0.4 里至少有三类"证据/义务"被刻意分开持有：

```
Gap state            → Gap / Feedback Interface（append-only history，单一 authoritative value）
fairness debt        → Scheduler-local 观测账（跨**调度周期**，但仍在当前任务内）
visibility commitment→ Notification-local 生命周期（当前任务内）
decision authority   → Interface §9.5/§10（外部主体只到 SUSPENDED 为止）
```

一旦把它们**跨会话持久化**，最自然的实现是搞一个**万能共享账本**，把
```
Gap state ＋ Fairness debt ＋ Notification commitment ＋ Decision authority ＋ History
```
塞进同一个 schema。**这会直接摧毁 V0.4 好不容易建立的 ownership**（E2/E7/E8 都会失效）。

### 因此，在谈任何 schema 之前先回答

> **哪些东西必须跨会话保持 identity，哪些只是当前 scheduler 的局部证据？**

**候选分层（仅作讨论框架）**

| 层 | 是否必须跨会话 | 理由（待证） |
|---|---|---|
| **作者身份 / 任务身份** | **必须**（否则"下次再说"无对象） | 相关性：承诺的对象要有稳定指称 |
| **Gap identity（+ generation）** | **可能必须** | 否则跨会话无法判断"同一缺口" |
| **User-visible commitment** | **视产品语义**（C2-04） | 与"要不要真的记得"耦合 |
| **Fairness debt** | **倾向不必** | 它是**当前调度竞争**的局部证据；跨会话延续会把"这一次的不公平"变成永久债 |
| **Decision authority** | **倾向不必** | 授权通常绑定一次决策会话；跨会话延续等于**永久代理权**（危险） |
| **History（append-only）** | **必须**（若存在跨会话） | 但**不必**与上面共用同一存储 |

### 危险判据（先定这个，再谈 schema）

任何一个"共享账本"提案，必须先通过：

```
① 它是否让某一层获得了对别层字段的写权？
② 去掉共享账本，哪个 case 会重新产生二义性？（对照协议 Q2）
③ 它是在**扩展** identity，还是把"局部证据"提升成"全局事实"？
```

**只要 ① 成立，该提案即被否决**（ownership 优先于便利）。

### 状态

```
UNDECIDABLE（当前证据不足）
—— 需要先有跨会话的真实案例（C2-04 只给了 1 例），不得据此设计。
```

## O-2 · 第三方主体（多主体决策权）

```
场景来源：C1-08（"你提三个，我挑，但最终得老板点头"）
```

V0.4 的 `pending_external` 能表达"等外部 owner"，但其**恢复语义**是
`SUSPENDED → OPEN → 用户确认`，**默认最终值归属仍是用户**。

**待研究（先案例后抽象）**

- "用户选择"与"外部批准"同时存在时，**用户的选择**是不是 `CONFIRMED`？
- 外部否决是否需要 `revert`／`challenged`（即是否触发有效性传播）？
- 这是"外部 owner"还是"**内部多主体**"（两者语义不同）？

**状态**：`V0.4-BOUNDARY`（多主体）＋ 待补案例（至少各 2 例：外部批准方、共同决策方）。

## O-3 · 交付完整性与 Notification 的 ownership

```
场景来源：C2-12（任务收尾时承诺未兑现）
```

V0.4 已明确：**任务结束前披露未完成内容属"交付完整性"责任**，**不由 starvation 触发 Notification**。

但**未兑现的 visibility commitment** 落在两层的交界：

| 选项 | 后果 |
|---|---|
| 归**交付完整性** | Notification 继续只管"承诺是否被履行"，不碰输出 |
| 归 **Notification** | 等于给了 Notification 改交付输出的口子 → **越权风险** |

**倾向**：归交付完整性；Notification 至多**提供输入**（"有一条承诺未兑现"）。
**状态**：`V0.4-AMBIGUOUS`（归属未写死）＋ 需补 ≥2 案例。

## O-4 · "用户声明约束"是否构成第三类授权边界

```
场景来源：C1-05（"只要不违法"）／C1-07（"不超过 5000"）／C1-10（"不许用红色"）
```

**这是 C1 里唯一"三次独立命中同一处"的模式**，且三次**均表现为解析不足**。

待研究：用户声明的约束是
```
① 授权的【作用域边界】（越界 → blocked，保持 OPEN）
② 硬门（与 R6 同级）
③ 只是偏好（越界仍可 assumed ＋ 标注）
```

**注意**：若最终选 ①，它可能**不需要任何新字段**——只需一条解析契约把"用户声明约束"接到既有 `scope`／风险门家族。
**状态**：`V0.4-AMBIGUOUS`（3 例同族，未定）。
