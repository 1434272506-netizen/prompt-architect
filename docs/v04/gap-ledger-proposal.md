# V0.4.1 · Gap Ledger 设计提案

> **阶段**：V0.4 Adaptive Requirement State Engine · **第一优先：缺口级统一账本**
> **本轮范围（用户裁决）**：**只做设计，不写 SKILL、不改冻结章节、不新增动作、不新增 Type、不继续补案例。**
> **验收标准（用户裁决）**：不是"增加了多少规则"，而是 **"一个新状态模型能否让多个失败案例自然消失"**。
>
> 上游证据：[../v04/failure-inventory.md](../v04/failure-inventory.md)（38 例 / 32 个真失效点 / 三个结构性空白）
> 冻结边界：[../freeze-v0.3.md](../freeze-v0.3.md)（24 个受保护文件本轮**零改动**）

## 0. 一句话架构判断

V0.3 解决的是"**如何消解一个未知**"；V0.4 要解决"**多个未知在时间中的生命周期**"。

```
V0.3：  Unknown → ASK / SHOW / INSPECT / TEACH / DISCOVER            （单步最优）
V0.4：  Gap → 产生 → 处理 → 确认 → 变化 → 失效 → 重新评估            （状态演化）
```

**根因诊断（本轮破坏测试的结论）**：V0.3 有**四本互不相通的账**——

| 账本 | 管什么 | 只管哪条通道 |
|---|---|---|
| §3.2 unresolved | 回避/不知道 | **只统计 ASK** |
| R7 | 用户答不出 | 只统计 SHOW |
| R12 | Type C 备注 | 只统计被降级的 C |
| §6.5 | Revision | 只统计"有修正信号"的变更 |

→ 同一个缺口可以**在 A 账本关闭、在 B 账本不存在、而需求实际并未稳定**。这不是四个 bug，是**没有单一事实来源（single source of truth）**。

**Gap Ledger 就是那个单一事实来源。**

## 1. Gap Entity 定义

**核心对象不是"需求字段"，而是"缺口"本身。**一个 Gap = 一个不确定点从产生到稳定的全过程。

```yaml
gap_id: G-001

# ── 身份 ────────────────────────────────
topic:        首页视觉方向          # 人可读标题（不是字段名）
kind:         style_cue            # 见 §1.2 分类（含 conflict_group / risk / env_fact…）
type:         Unknown_Known        # 复用 V0.3 的 Type A–E（不新增）

# ── 来源与依据 ──────────────────────────
source:       user_statement       # user_statement | env_readable | ai_inference | risk_scan
evidence:     用户原话"要高级"      # 判定依据（可追溯到原文/文件行）
blocking:     false                # 是否 R6 阻塞项（复用 V0.3 R6 闭集）

# ── 生命周期（见 §2）────────────────────
status:       OPEN                 # OPEN | PROPOSED | SUSPENDED | CONFIRMED | CHALLENGED | INVALIDATED | CLOSED
resolution:   shown                # asked | shown | inspected | taught | discovered（复用 V0.3 五值）

# ── 当前值（关键新增）──────────────────
current_value:  —                  # 「现在生效的值」——V0.3 缺失的语义
provenance:     —                  # 这个值从哪来：用户选择 / 用户原话 / 环境事实 / AI 默认
confidence:     unconfirmed        # confirmed | assumed | partial | unconfirmed

# ── 关系（见 §4）────────────────────────
dependencies:  [G-003]             # 本缺口的值依赖哪些上游缺口
affected:      [homepage_style, color_system]   # 本缺口的值一旦变化，会影响哪些下游
supersedes:    —                   # 被本 gap 取代的旧 gap（Revision 产物）
targets:       [cover_v2, hero_section]         # 已被本 gap 影响的**已产出物**（见 §4.3 效力位）

# ── 反馈账（关键新增）────────────────────
attempts:      1                   # 已尝试消解的次数（见 §5.1 计数口径）
last_resolution: shown
feedback:      no_signal           # 见 §5 反馈账
feedback_count: {no_signal: 1}

# ── 历史（只追加，不改写）────────────────
history:
  - {t: 1,  event: created,   by: user_statement}
  - {t: 3,  event: shown,     detail: "3 个方向"}
  - {t: 4,  event: no_signal}
```

### 1.2 `kind` 分类（本轮补齐，修 C-05）

**V0.3 的失败点里，有一类"缺口"其实不是未知，而是"两条要求互相打架"** —— 它需要一个可寻址的对象，否则永远悬置（C-05：冲突组"暂停"后无计数器、无终态）。

| kind | 含义 | 典型来源 | 终态条件 |
|---|---|---|---|
| `deliverable` | 产物锚点 | §2.5 P0 | 用户确认 / 环境核实 |
| `audience` | 受众 | §2.5 P0 | 同上 |
| `success` | 成功标准 | §2.5 P0 | 同上 |
| `constraint` | 硬约束（P2） | §2.5 P2 | 同上 |
| `style_cue` | 模糊审美（Type B） | §4 模糊词 | SHOW 收敛 / 达 attempts 上限 |
| `risk` | 风险类（Type C） | §3.1 R14 | TEACH 后 ASK / 「暂不做」 |
| `env_fact` | 环境事实（Type E） | §2.5 | INSPECT 核实 |
| **`conflict_group`** | **两条要求互斥（§3.1 Conflict）** | §3.1 | **VAL 或 INVALIDATED 或 SUSPENDED→CLOSED** |
| `revision` | 用户明确改需求（§6.5A） | §6.5 | 下游重开完成 |

> **`conflict_group` 是本轮新增的对象化**：它把"冲突组暂停"从一句叙述变成**有 id、有状态、有计数、有终态**的对象。
> 没有它，C-05 的"三个互斥说法被合法清空"无法被阻止。

### 1.3 明确边界（防止变成数据库）

- **它不是持久化存储**：是**认知模型**——用于"当前该做什么、什么还成立"的推理；落盘只是可选产物（沿用 V0.3 的"待确认假设 / 决策记录"出口）。
- **不新增 Type**：`type` 字段直接复用 V0.3 的 A–E。
- **不新增动作**：`resolution` 字段直接复用 V0.3 的 ASK/SHOW/INSPECT/TEACH/DISCOVER。
- **不取代 §6.6 决策记录**：见 §3。

## 2. Gap 生命周期（六态）

```
                    ┌──────────── 用户新信息 / 上游变化 ────────────┐
                    │                                              │
                    v                                              │
  ┌────────┐  动作   ┌──────────┐  用户确认  ┌───────────┐  重新评估 ┌────────────┐
  │  OPEN  │ ──────> │ PROPOSED │ ────────> │ CONFIRMED │ ───────> │ CHALLENGED │
  └────────┘  消解   └──────────┘           └───────────┘          └────────────┘
      │                   │                      │                    │
      │ 可直接确认         │ 反馈=回避/无信号       │ 上游失效            ├──> VALID   （值仍成立）
      │（环境事实/用户原话）│                      │                    └──> INVALIDATED（值作废）
      v                   v                      v                         │
  ┌──────────────────────────────────────────────────────────────┐      v
  │                        CLOSED                                │   重新 OPEN（重新消解）
  │（已确认 / 已假设 / 已失效 / 已放弃 —— 由 confidence 区分）      │
  └──────────────────────────────────────────────────────────────┘
                                ▲
                                │ 澄清被回避 1 次且 conflict_group 未解
                    ┌────────────┴──────────┐
                    │      SUSPENDED        │  ← 本轮新增第 7 态（修 C-05）
                    │ 冲突组已挂起，入账计时  │
                    └───────────────────────┘
```

| 状态 | 含义 | 谁能进入 | 出口 |
|---|---|---|---|
| **OPEN** | 识别到缺口，尚未处理 | §2.5 分类后 | → PROPOSED（发动作）/ → CONFIRMED（环境事实或用户原话直接给出） |
| **PROPOSED** | 已发出消解动作，等反馈 | 任何动作发出后 | → CONFIRMED（用户确认）/ → OPEN（反馈=无法判断，换动作）/ → SUSPENDED（反馈=回避，见下）/ → **CLOSED(assumed)**（反馈=无信号且达上限） |
| **SUSPENDED** | **冲突组已挂起 / 澄清被回避**（V0.3 的"该冲突组暂停"的对象化） | ① `kind=conflict_group` 判 Conflict 后；② `feedback=evaded` 且缺口阻塞 | → OPEN（用户回到该话题）/ → CLOSED(assumed) （回避达上限）/ → INVALIDATED（冲突因上游变化消失） |
| **CONFIRMED** | 值已确定 | 用户确认 / 证据核实 | → CHALLENGED（新信息或上游变化） |
| **CHALLENGED** | 值受质疑，待重新评估 | 新信息、Revision、上游 INVALIDATED | → VALID（恢复 CONFIRMED）/ → INVALIDATED |
| **INVALIDATED** | 旧值作废 | 评估判定不成立 | → OPEN（该缺口需重新消解） |
| **CLOSED** | 终态（不再活跃） | 确认/假设/失效/放弃 | 由 `confidence` 区分是"已确认"还是"已假设" |

**两个关键区分（V0.3 缺失的）**：
1. `CLOSED` **不等于**"需求已稳定" —— 由 `confidence` 分成 `confirmed | assumed | partial`
   → 直接修掉 **F4-05/F4-06**：用户问"现在哪些还生效"时，答案 = **`status=CONFIRMED and confidence=confirmed` 的集合**。
2. **`SUSPENDED` 是一个"入账状态"，不是"遗忘状态"** —— 它在 `attempts`/`feedback_count` 里被计数，并有出口时限
   → 直接修掉 **C-05**：冲突组不再"暂停即消失"，三个互斥说法不会被 §8"留空"合法清空。

### 2.1 状态判定谓词（可证伪，供测试直接引用）

```
生效集合        := { g | g.status = CONFIRMED  ∧ g.confidence = confirmed }
假设集合        := { g | g.status = CLOSED     ∧ g.confidence ∈ {assumed, partial} }
活跃缺口        := { g | g.status ∈ {OPEN, PROPOSED, SUSPENDED, CHALLENGED} }
阻塞且悬置      := { g | g.status = SUSPENDED  ∧ g.blocking = true }     ← 禁止静默出稿
禁止再用同一动作 := attempts ≥ 2 ∧ feedback ∈ {no_signal, unable, evaded}
```

> **可证伪性（重跑方要求）**：删掉 `confidence` 字段 → 授权默认项会与用户确认项一起被判"生效"，**生效集合立刻出错**；删掉 `SUSPENDED` → C-05 症状立刻回来。

## 3. 与既有机制的关系（**不取代，只统一**）

| V0.3 机制 | 关系 | 规则（本轮只描述，不写入 SKILL） |
|---|---|---|
| **§3.2 unresolved** | **被 Gap Ledger 吸收** | 不再有独立计数器：`feedback=evaded/unknown` 即产生 `feedback_count`。**"连续 2 次"改读 `attempts` + `feedback_count`**，且**覆盖所有通道**（修掉"只统计 ASK"的洞） |
| **R7 两轮上限** | **成为通用规则** | 从"Type B 专属"升级为**任何 resolution 的通用上限**：`attempts ≥ 2 且 feedback ∈ {no_signal, unable}` → **禁止再用同一 resolution**，转其他动作或落 `assumed` |
| **R12 Type C 备注** | **成为 gap 的一个子集** | `status=CLOSED, confidence=assumed, kind=risk` 的 gap；"1–2 轮内 TEACH 或标暂不做"改读 **gap 的 `challenged → 处理时限`** |
| **§6.5 Revision** | **只读，不修改** | Revision 仍是 §6.5 的判定；**但结果写入 gap 图**：产生 `supersedes` 边 + 下游标记 `CHALLENGED`。**本轮不动 §6.5**（第三优先，Phase 3 再决定是否触碰） |
| **§6.6 决策记录** | **降级为"快照"** | gap 是**活账**（每步更新），决策记录是**审计痕**（只追加）。二者分工：**推理读 gap，复盘读决策记录**。允许重复，禁止互斥 |
| **§7 双轨标记** | **成为 gap 的 `provenance`** | "AI 建议 vs 用户需求" = `provenance ∈ {ai_inference} vs {user_statement, user_selection}`。**§7 铁律不变**，只是有了字段承载 |

**一致性约束（防两账打架）**：
1. 任何 gap 的状态变化**必须**同时产生一条决策记录（保持 §6.6 可审计）
2. 决策记录**不得**持有 gap 没有的状态（禁止影子账本）
3. 出口（§8 的「待确认假设」区）**只渲染** `confidence ∈ {assumed, partial}` 的 gap，不重新计算

## 4. 依赖与失效传播（**Validity Layer 最小版**）

Phase 1 **只需**最小能力：**记录依赖 + 标记下游**，**不重算**（重算属 Phase 3）。

```yaml
G-003 品牌定位 = 东方美学   [CONFIRMED]
   ↓ affects
G-001 首页视觉方向 = 东方雅致   [CONFIRMED]
G-007 色彩系统
G-009 摄影方向
```

当 G-003 被 `CHALLENGED`（用户："改成面向欧美市场"）：

```
G-003 → CHALLENGED
   ↓ 传播（只标记，不判定值）
G-001 / G-007 / G-009 → CHALLENGED   ← 解决 G-01/G-02「局部不可判定」
```

**"局部"的定义（本轮给出）**：局部 = **`affected` 闭包**（含传递闭包），不是"我以为没影响的部分"。
→ 这直接修掉 **G-01（P0 推翻时"局部"不可判定）** 与 **G-02（换受众时视觉方向被误判未受影响）**：
**受影响集合是可枚举、可证伪、可验收的**。

### 4.1 ⚠️ 依赖图的填充规则（**重跑方指出的关键缺口：无规则的图 = 空图 = 退回 V0.3**）

**问题**：用户只说一句"改成面向欧美市场"，系统凭什么知道要标 `G-007 色彩系统`、`G-009 摄影方向`？
如果依赖图是"AI 现场推断"的，那 G-01/G-02 的"可枚举"就**只是把不确定性挪了个位置**。

**本轮给出的填充规则（不靠现场推断，靠固定维度表）**：

1. **`dependencies`/`affected` 不自由生成**，而是从 **固定维度表**（V0.3 §5 核心对象七问的维度轴）派生：
   `产物锚点 / 受众 / 成功标准 / 视觉语言 / 色彩 / 文案 / 素材来源 / 技术约束 / 合规`
2. **建立时机是"缺口创建时"**，不是"变更时"：每个新 gap 创建时必须回答"它挂在哪个维度轴上、它的上游是哪个已确认 gap"。
3. **传播规则固定**：`CHALLENGED` 沿**同轴向下**与**已声明依赖边**传播，**不做语义猜测**。
4. **保守默认（防漏）**：若某 gap 无法确定上游，则**默认从属于"产物锚点"**（P0 锚点），即**锚点一变，它必须被重新评估** —— 宁可多标，不可漏标。
5. **可验收性**：受影响集合 = **闭包计算结果**，可以被用户直接核对（"这些是会被影响的，对吗？"），也可被测试断言（给定图 → 期望闭包）。

> **这条规则把"AI 推断"换成"结构性传播"**：图不是猜出来的，是按维度表**填**出来的；漏标会被规则 4 的保守默认兜住。

### 4.2 `CHALLENGED` 期间的值效力（**决定 G-01/G-04 能否判 SOLVED**）

| 状态 | 旧值（`current_value`）能否被出稿读取 |
|---|---|
| `CONFIRMED` | ✅ 可以，直接使用 |
| `CHALLENGED` | ❌ **不得直接使用**；必须在出口标注该值"受质疑、待重新评估"，或先走重新评估 |
| `INVALIDATED` | ❌ 禁止使用，按 `status=OPEN` 重新消解 |
| `SUSPENDED` 且 `blocking=true` | ❌ **禁止静默出稿**（这是 F3/S-03 的防线） |

> **没有这条，就会出现"有标记但仍搬过去"的新中间态** —— 症状与 V0.3 同形（G-04 的判 PARTIAL 主因）。

### 4.3 `targets`：已产出物的效力位（**重跑方指出它此前只在叙述里，未进字段集**）

```yaml
targets:
  - {artifact: cover_v2,        status: affected_by_G-003, action: "重开第 2 节"}
  - {artifact: hero_section,    status: affected_by_G-003, action: "作废并重画"}
```

- 每次 gap 进入 `CHALLENGED`，**必须**把已产出物登记进 `targets`（否则用户不知道旧稿哪一段还算数）
- 出口时按 `targets` 生成"**旧稿效力清单**"：哪些段落作废、哪些仍有效
- **这是 G-04（出稿后推翻 P0 产物：旧稿效力无判定）的直接承载**

**边界（Phase 1 不做）**：不判定"新值是否与旧值兼容"（那是 §3.1 的活）；不自动重算下游值（留给 Phase 3）。

### 4.4 ⚠️ 缺失的边不留痕迹（**覆盖复核的最强一击，必须承认并处理**）

**覆盖复核的论证**：`dependencies/affected` 只是两个字符串数组，**边没有 `evidence`/`source` 字段**；§4 那张 `G-003 → G-001/G-007/G-009` 的图是**设计者手写的**。
→ 用户只说"改成面向欧美市场"时，要标 `G-007 色彩系统`、`G-009 摄影方向`，**前提是那两条边已经存在**——而建边的主体只能是 AI 自己。
→ 结论：**"可枚举"= 图完备性 = AI 推断完备性**，不是新能力，而是把 §6.5C 的"逐项检查"换成"逐边检查"；而**缺失的边不留任何痕迹** —— V0.3 至少会说一句"其余不变"（用户可反驳），账本却会**沉默地不标**，于是**可证伪性下降、并产生虚假置信**。

**本轮的处理（三条，都必须有）**：

1. **边必须带证据**：
   ```yaml
   affected:
     - {target: color_system, evidence: "用户原话'东方美学'→色彩在此语境下由该定位派生", source: ai_inference}
   ```
   `source ∈ {user_statement, env_readable, ai_inference}` —— 与 gap 的 `provenance` 同构。
2. **必须显式保留"未建模依赖"**：每个 gap 增加 `unmodeled_dependencies: []`（默认空，但**出口必须渲染**）。
   含义：**"我没找到的依赖"是一个必须被说出来的事实，而不是沉默**。
3. **出口必须输出"本次受影响集合"**：不能只渲染 `assumed/partial` 的 gap（v0 的一致性约束 3 只做了这件事），否则**可验收无承载物**。
   出口格式：`已标记受影响：A / B / C；未建模的潜在依赖：D（建议你确认）`。

> **承认的代价**：`G-01/G-02` 因此**不能算 SOLVED**，只能是 ⚠️ **部分** —— 账本把问题从"逐项自查"变成"逐边自查 + 显式保留未建模项"，**这比 V0.3 好，但不是新能力**。**虚假置信比不确定性更危险**，这一点必须写进结论。

## 5. 反馈账（Feedback Ledger）—— 与 Phase 2 的接口

Phase 1 **只定义字段与写入时机**，**不做分类器**（分类器是 Phase 2）。

| 字段 | 取值 | 写入时机 |
|---|---|---|
| `attempts` | 整数 | 每次发出 resolution +1 |
| `last_resolution` | 五动作之一 | 每次动作发出时覆盖 |
| `feedback` | `none \| accepted \| selected \| no_signal \| evaded \| unable \| refused \| disagreed \| revised` | 收到用户反应时 |
| `feedback_count` | 各反馈类型计数 | 累加 |

### 5.1 计数口径（**两路独立复核共同指出的首要缺陷，必须钉死**）

```
attempts              = 该 gap 上「发出过 resolution 的次数」（动作侧，只增）
consecutive_no_signal = 该 gap 上「连续无产出反馈」的次数（反馈侧，遇产出性信号即清零）
feedback_count        = 各类型反馈的累计计数
```

**⚠️ 为什么不能用 `attempts ≥ 2` 当闸门（v0 的错）**：
> F1-02 的第 3–4 轮**用户根本没有回应**，系统也**没有发出新动作** → 按"每次发出 resolution +1"的定义，`attempts` 停在 1 → **闸门永不复位，第三次 SHOW 依然合法**。
> 即：**这个通用上限在它被设计来解决的第一个案例上就不可判定。**（重跑方与覆盖复核**独立**在这一点上收敛）

**修正后的闸门（前件改为反馈侧字段）**：

```
禁止再用同一动作 := consecutive_no_signal ≥ 2 ∧ last_resolution 连续两次相同
复位条件        := 收到任意产出性反馈（accepted | selected | revised | disagreed）
                  或 gap 进入 CONFIRMED / CHALLENGED  → consecutive_no_signal 清零
```

**其余两条约束（覆盖复核提出）**：
1. **保留 R7 的"提高保真度"前置**：禁止重复**同一保真度**的动作；提高保真度后允许再发一次（否则会把 V0.3 明确允许的升级路径判违规）。
2. **TEACH 豁免**：与 §2.5 规则 4「同一维度 ≤1 次、用户主动追问可再讲 1 次」对齐 —— `resolution=taught` 时闸门阈值放宽为"用户主动追问可续 1 次"，不适用上面的通用闸门。

**Phase 1 直接用到的两条迁移规则（来自本轮失效点）**：
1. **F1-02 空转**：`last_resolution=shown ∧ consecutive_no_signal ≥ 2` → **禁止第三次同保真度 SHOW**，转 ASK、提高保真度、或落 `assumed`
2. **F3-06/S-03 拒答循环**：`feedback=refused ∧ gap.blocking=true` → **不再重复请拍板**，落 `CLOSED(assumed)` + 显式标注「用户拒绝提供」，并触发 §7 铁律（不得伪装成用户需求）

### 5.2 `CHALLENGED` 的 Phase 1 出口（**覆盖复核指出：v0 里它没有出口，账本会自己生产悬空态**）

**v0 缺陷**：`CHALLENGED` 的唯一出口写的是"重新评估"，而 §4 明文"Phase 1 不重算" → 上游每失效一次就生产一批**没有出口的 `CHALLENGED`**，等于账本自己重生它要修的 F1-04（悬空），且用户看不见。

**修正**：Phase 1 提供**最小判定出口（不是重算）**——只做"标记 + 人工确认"，不做值推理：

```
CHALLENGED 的 Phase 1 出口（三选一，必须选）：
  a) 用户确认"旧值仍适用"      → 回 CONFIRMED
  b) 用户确认"旧值不再适用"    → INVALIDATED → OPEN（重新消解）
  c) 超时未确认（≥2 轮未处理） → 标 CLOSED(partial) + 在出口显式列出「待重新评估」
禁止：停留在 CHALLENGED 超过 2 轮而不做出上述任一选择。
```

**配套字段（覆盖复核提出，成本低但必要）**：
- `current_value.confirmed_at`（轮次号）：否则用户看到的"已确认"是**无时间戳的断言**，不可用于"拿去跟合伙人确认"（F4-05 的原始用途）。
- `history[].seq`（轮内序号）：同轮两次更新需要定序，否则"并发状态互相覆盖"无法复盘。
- `unmodeled_dependencies`（**显式保留位**）：见 §4.4。
