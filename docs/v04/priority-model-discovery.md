# V0.4.4 · Priority Model Discovery（30 例破坏测试）

> **阶段性质**：**只做破坏测试，不写规则。**
> **目标**：① 确定 **Priority Layer 的职责边界**；② 验证 **`deprioritized` 是否应作为纯调度属性**。
> **禁止**：修改 §11／V0.3／Interface v1／v2／v3／§10；新增 Action／Type／Gap state；**设计数值评分**。

**被测对象与硬约束**

| 层 | 角色 |
|---|---|
| **Priority Layer（本轮待定义）** | 在"已由 V0.3 §11.0 选出动作"之后，决定**先做哪一个** |
| V0.3 §11.0 规则 1–8 | 动作选择优先于问题排序；INSPECT → SHOW → TEACH → ASK；P0 语义例外 |
| V0.3 契约 R4 | 同轮容量（≤1 TEACH + 1 SHOW + 1 ASK）与顺序 |
| V0.3 契约 R6 | 阻塞项必须用户拍板、**不可 DISCOVER** |
| V0.3 契约 R14 | 高风险 C 前置：三闸门 + **与阻塞项同轮并列**，不得推迟 |
| V0.3 契约 R2 / §11.7 | 每轮 1–3 问；合并按实际子问题计数 |
| §11.1 / §11.6 | 同层二次裁界（可回答性）；**上游依赖优先** |
| Interface §1.2 / §5 / §10 | `askable_set`；**动作闸门 > 形式选择**；Contract 出口由 intent＋② 判定 |
| Phase 2.3-B | `deprioritized`（候选纯调度属性，尚未入接口） |

**每例记录 9 项**：① 当前 active gaps｜② 各 gap 的 state／blocking／risk／dependency｜③ 用户显式优先级表达｜④ V0.3 已选 action｜⑤ 当前应优先处理谁｜⑥ §11 是否参与｜⑦ 是否改变 gap 状态｜⑧ 是否与冻结规则冲突｜⑨ 是否需要新字段。

| **P5-02** | 高风险 C + 阻塞项 | `先做阻塞项。` | TEACH + ASK | **同轮并列**（R14，TEACH 恒先于 ASK） | 是 | 否 | 无 | 否 |
| **P5-03** | SHOW 待反应 + 新 ASK 候选 | `直接问吧。` | SHOW（未处理完） | **不得展开 ASK**（R4：SHOW 结果未处理完不展开 ASK） | 是 | 否 | 无（用户偏好被 R4 吸收） | 否 |
| **P5-04** | 5 个同层候选问句（容量 3） | `按你说的来。` | ASK ≤3 | 用 §11.1 一级（排除下游最多）＋二级（可回答性）选 3；**用户授权不改判据** | 是 | 否 | 无 | 否 |
| **P5-05** | 阻塞项 + 非阻塞可探索项 | `先探索。` | ASK（阻塞）vs DISCOVER（非阻塞） | **阻塞项走 ASK**（R6：不可 DISCOVER）；探索项随后 | 是 | 否 | 无 | 否 |

## 结论 A · Priority Layer 的职责边界

```
输入：  active gaps（含 state / blocking / risk / dependency）
        ＋ 已由 V0.3 §11.0 选出的合法动作集合（经 R4／R6／R14 过滤）
        ＋ 用户显式优先级（若有）
        ＋ 同轮容量（1–3）
   ↓
输出：  有序 action 队列（先做哪个；同轮放哪几个）
```

| 允许 | 禁止 |
|---|---|
| 排序、分组（同轮并列）、容量内的取舍 | ❌ 决定"要不要做某个动作"（属 V0.3 §11.0） |
| 读取 `blocking`／`risk`／`dependency` 作为**硬约束过滤条件** | ❌ 覆盖 R4 顺序／R6 闭集／R14 前置 |
| 接受用户显式优先级作为**排序偏好** | ❌ **改写 gap 状态**（状态只由 Interface §8／§9／§10 的门与跃迁决定） |
| 在容量内做取舍并在出口说明 | ❌ **数值评分**（本轮明确禁止设计） |

**一句话**：**Priority 层是"调度器"，不是"决策器"**——它回答"先做哪个"，不回答"做不做"或"状态变不变"。

## 结论 B · `deprioritized` 是否应作为**纯调度属性**

**结论：是——但必须与"延后／放弃"严格区分。**

| 表达 | 归属 | 是否改状态 |
|---|---|---|
| **降权**（"不重要"／"随便"／"以后再说"的对象被降序） | **`deprioritized`（纯调度属性）** | **否**（P1-02／P1-03／P3-05／P2-03） |
| **延后**（"以后再说"作为**决定**） | **delay → `OPEN + deferred`**（Interface §3，已有） | **是**（P1-06／P2-02） |
| **放弃** | 走 Refused／assumed（Interface §10，已有） | 是 |

**三条边界（本轮由测试证明）**

1. **降权不能作用于阻塞／R6／高风险 C**（P2-01／P2-05／P2-06）：被硬约束吸收，且**不改变状态**。
2. **降权会传播到下游效力**（P4-06）：上游被降权不直接改状态，但一旦上游变更，下游按 Interface §9 统一重评——**传播不属 Priority 层**。
3. **`deprioritized` 不参与"是否继续提问"**：它只影响顺序；"还能不能再问"由 Interface §5 动作闸门与 §10 Contract 决定。

## 冲突与字段需求

### 与冻结规则的冲突：**0 例**

30 例中没有出现"两条冻结规则给出相反动作"的情形。曾被怀疑的三处，本轮判明**不是冲突**：

| 疑点 | 判定 |
|---|---|
| P3-06：授权默认（§6.3「不再追问」）vs 先教再问（R3） | **不冲突**：R3 管"告知"（TEACH 非追问），§6.3 管"是否追问" → `TEACH` 后直接 assumed，不再 ASK |
| P4-01／P4-03：用户显式序 vs 上游依赖（§11.6） | **不冲突**：依赖是**硬约束**，用户偏好不是规则；依赖胜，且需用户可见说明 |
| P5-03／P5-05：用户偏好 vs R4 顺序／R6 闭集 | **不冲突**：用户偏好被 R4／R6 吸收（硬约束优先） |

### 是否需要新字段

| 需求 | 结论 |
|---|---|
| **用户显式优先级（顺序）** | **需要一个承载位**：`deprioritized`（bool）**表达不了**"先 A 后 B"这类**相对序**。候选名 **`priority_hint`（有序，非数值）**；**不设计分值／权重**（本轮禁止） |
| 其余（blocking／risk／dependency／state） | **复用现有字段**，**无需新增**（`blocking`、`risk`/Type C、`dependencies`、`status`／`validity_state` 已足） |
| 跨 action 竞争的排序结果 | **不需要持久字段**（是每轮派生物，不是需求状态） |
