### 1.1 F1-02 · 连续两轮 SHOW 无人回应后出现合法但纯空转的第三次 SHOW

**① 原始多轮输入**
```
第 1 轮：做一个高级官网，给海外客户看的
第 2 轮（收到 3 个方向后）：先不急，我还想加个博客板块
第 3 轮：嗯
第 4 轮：（只回三个方向里 B 的一个 👍，无文字）
第 5 轮：算了你看着办
```

**② V0.3 下的失败动作链**
1. 第 1 轮首轮 → §2 采访循环，命中 Type B → SHOW 一轮。
2. 第 2 轮"先不急，还想加博客板块"：契约 **R8**「SHOW 无反应按未答处理」（`core/uncertainty-classifier.md` §5 R8）+ §3.2「用户顺带给出的其他有效信息照常吸收保存」→ 新增信息吸收，方向缺口记"未答"。
3. 第 3 轮"嗯"、第 4 轮"👍"：同按 R8 记未答。
4. **冲突点**：**R7**「SHOW 一轮后用户仍无法判断 → 提高保真度再 SHOW 一次；两轮仍不行才走默认值」的前提是用户给出了"无法判断"**这个反应**；本案用户从未给过反应。而 §2.5 生效方式行明写「**§3.2 的 unresolved 只统计 ASK 通道**」→ SHOW 通道的"未答"不在任何计数器里 ⇒ 无上限、无终止态。
5. 第 4 轮输出：**又一版提高保真度的方向扇**（配色块 + 版式示意），在用户零输入下继续消耗轮次。
6. 第 5 轮"算了你看着办"才落 §6.3 授权默认 → 出稿。
→ 命中：**规则相反**（R8 与 R7 对"无反应"的计数归属不一致）+ **③无限消耗**。

**③ 套用 Gap Ledger 后的动作链**
1. **t1**：识别缺口 `G-001 topic=首页视觉方向, kind=style_cue, type=B, source=user_statement, evidence="要高级/给海外客户", blocking=false` → `status=OPEN`。
2. **t2**：SHOW 三方向发出 → 迁移 `OPEN → PROPOSED`，写 `resolution=shown`、`attempts=1`、`last_resolution=shown`。
3. **t2 反馈**：用户"先不急，加个博客板块"= 未回答本缺口（可能取值 `no_signal` 或 `evaded`）→ 写 `feedback=no_signal`（按 failure-inventory §4 对 F1-04 的裁定口径），`feedback_count{no_signal}=1`；"博客板块"另起一个 gap 吸收。状态留在 `PROPOSED`。
4. **t3**"嗯" → `feedback_count{no_signal}=2`（`attempts` 仍为 1：本轮未发新动作）。
5. **t4**（准备再 SHOW 时）：命中 **§5 迁移规则 1** 的前件 —— `last_resolution=shown ∧ feedback=no_signal`，且"连续无法获得有效反馈"的计数已达上限（等价于 R7 的两轮窗口）⇒ **禁止第三次 SHOW**。
   → 迁移 `PROPOSED → CLOSED`，`confidence=assumed`（§2 表：PROPOSED →「反馈=无信号且达上限」→ CLOSED(assumed)）。
6. **t4 动作**：转入另一 resolution（ASK 或落默认值）；缺口按 §3 一致性约束第 3 条进入出口（`confidence=assumed` 才渲染）。
7. **t5**"算了你看着办" → 命中 §6.3 授权默认。**注意**：此时 `G-001` 已在 t4 为 `CLOSED(assumed)`，t5 不产生新的消解动作，只是把既有 assumed 值显式化（不构成重复追问）。

**④ 判定：SOLVED**

**⑤ 关键状态位（为什么旧失效不可能发生）**
- 阻止第三次 SHOW 的不是"流程更合理"，而是 **§5 迁移规则 1 的前件是一个可验证的三元组**：`last_resolution=shown` ∧ `feedback=no_signal` ∧ `feedback_count` 达上限。
- V0.3 做不到这一点的根因是**该三元组无承载**：契约 R8 只产出"未答"这个**语义**，§3.2 的计数器被 §2.5 明文关在 ASK 通道内。Ledger 把 `attempts / last_resolution / feedback / feedback_count` 归到 **gap 对象**上（`gap_id=G-001`），于是"SHOW 通道无计数"这一条**在字段层就不成立**——计数不再按通道分账。
- 对应失败点原文"窗口的起算与耗尽没有对应状态位"被直接消掉：起算 = `attempts` 自增，耗尽 = `CLOSED`。

**⑥ 残余（不改变 SOLVED，但记录在案，见 §4 与 §3）**
- `attempts` 与 `feedback_count` 是**两个**计数器，提案未写二者是否必须同步自增（"嗯"这种无动作轮次只加 `feedback_count`）——若实现者把上限挂在 `attempts≥2` 上，本案在 t4 时 `attempts` 仍为 1，闸门不复位。此为实现口径风险，非状态位缺失。

### 1.2 F1-04 · 用户岔开话题且再也不回来，方向缺口悬空到第 20 轮

**① 原始多轮输入**
```
第 1 轮：帮我做个作品集网站，要高级
第 2 轮（收到 3 个方向后）：对了，后端你用 Python 还是 Node 写？还有部署到哪儿？
第 3–19 轮：用户全程只在讨论技术栈、服务器、域名、数据库、SEO
第 20 轮：行，就按你说的做
```

**② V0.3 下的失败动作链**
1. 第 1 轮 Type B → SHOW；第 2 轮用户换话题 → 契约 **R8** 按未答处理，方向缺口状态停留「待决定」。
2. 第 2 轮抛出的技术栈问题按 §2.5 Step 4 → Type A → ASK（部署位置可能 Type E → INSPECT，契约 R1）。
3. §3.2「继续处理当前最高优先级缺口」+ 第 2 轮以后每轮都有**新的可吸收信息** ⇒ 方向缺口被合法地一轮一轮往后放，共 18 轮。
4. §6.6 决策记录只记「待决定」，**没有**"被挂起 / 被取代 / 已过期"的取值；§3.2 的 2 次分流只针对"答非所问"且只覆盖 ASK 通道。
5. 第 20 轮"就按你说的做" → §6.3 授权默认 → 出稿；方向缺口由默认值顶替，用户全程不知道"高级"最终按什么落地；该行混在「待确认假设」里与正式需求同层。
→ 命中：**无状态位**（挂起/过期）+ **④静默丢失**。

**③ 套用 Gap Ledger 后的动作链**
1. **t1**：`G-001 topic=整体视觉方向（作品集）, type=B, evidence="要高级"` → `OPEN` → SHOW → `PROPOSED, resolution=shown, attempts=1`。
2. **t2**：用户以新问题回应 = 未回答本缺口 → 记 `feedback=evaded`（提案 §5 闭集含 `evaded`，原文"明显回避"也在 §3.2 列举中），`feedback_count{evaded}=1`；技术栈缺口另建 gap（`source=user_statement`）。
3. **t3–t19**：每个技术缺口按 `type=A/E` 走 ASK/INSPECT，各自 `attempts` 自增并最终 `CONFIRMED`；`G-001` **未被删除**，`status=PROPOSED` 持续存在（这正是 V0.3 缺的"悬空但不消失"）。
4. **t20**"就按你说的做" → §6.3 授权默认。此时 `G-001` 仍在账上，写 `current_value=默认方向, provenance=ai_inference, confidence=assumed`，`status=CLOSED`；按 §3 一致性约束第 3 条，它**必须**出现在出口的「待确认假设」区（`confidence=assumed`）。
5. **可查性**：第 20 轮出稿时，"哪些是 assumed"是一次谓词枚举，而不是靠回忆。
→ 缺口**不再静默丢失**（有 status 存续 + 有 provenance 标注）。

**④ 判定：PARTIAL**

**⑥ 还缺什么**
1. **缺"搁置轮数"状态位**。提案 §1 有 `attempts`（已尝试消解次数），但**没有**"自上次动作以来被搁置了多少轮"。第 2 轮的 `feedback_count{evaded}=1` 到第 20 轮仍然是 1 —— Ledger 让缺口**可见**，但没有任何东西让它**重新回到台面**。原始失效点原文要求的是"被连续多少轮搁置就必须显式回台"的计数，该字段在提案里不存在。
2. **缺"过期未决"的呈现契约**。原始失效点要求"过期未决在出稿时以与用户确认不同的可见层级呈现"。提案 §3 约束 3 只规定出口渲染 `confidence ∈ {assumed, partial}` 的 gap，未定义层级/分组；§8 现有「待确认假设」是**一条一行**。同一类 assumed 里，"用户从未表态的核心槽位"与"AI 自己填的措辞细节"仍可能同层。
3. **`resolution=shown` 的 gap 悬置 18 轮后是否可再次消除（re-PROPOSE）**，提案未规定。若不禁止，执行者仍可选择在第 20 轮再来一次 SHOW（虽然此时 §6.3 已接管），本案例的"重新回到台面"就依赖自由裁量。

### 1.3 F1-05 · 用户选了方向后又给出与三方向都不符的描述

**① 原始多轮输入**
```
第 1 轮：做个品牌短片，要电影感
第 2 轮（收到 3 个方向后）：都不是我要的。我想要那种"静止里有暗流"的感觉，你别再给我选项了
第 3 轮：暗流就是表面很平静，但看着心里发紧
```

**② V0.3 下的失败动作链**
1. 第 1 轮 Type B → SHOW（两轮额度用掉 1 轮）。
2. 第 2 轮用户给出"第四条路"：§4「注意」明写"用户给出第四条路时必须欣然接受并优先采用"，`strategies/show.md` 第 7 步同 → 要求**就地接受**。
3. 同一句话触发契约 **R9**「发现即重分类」：`静止里有暗流` 是形容词/感受（Type B 判据）→ 重跑决策树 → 命中 SHOW。R9 又要求"不得沿用旧分类"。
4. 第 3 轮"暗流就是…"再次命中 Type B ⇒ 再给一组正交方向；同时 §2.5 规则 2 的"两轮 SHOW"额度已用 1 轮，再 SHOW 踩上限。
→ 两条规则（§4 注意 vs R9）对同一句话给出相反动作；用户"你别再给我选项了"这一明确声明**不构成任何可记录约束**。
→ 命中：**规则相反** + **判定歧义**。

**③ 套用 Gap Ledger 后的动作链**
1. **t1**：`G-001 topic=短片视觉基调, type=B, evidence="电影感"` → `OPEN` → SHOW → `PROPOSED, resolution=shown, attempts=1`。
2. **t2**：用户回"都不是我要的 + 静止里有暗流"。
   - **若要表达收敛**：`PROPOSED → CONFIRMED`（值 = 用户自述的"静止里有暗流"，`provenance=user_statement`，`confidence=confirmed`）。此时 `G-001.status=CONFIRMED` ⇒ 已收敛的问题集**不会**再产生 SHOW 迁移。
   - **若要表达重开**：新建 `G-002 topic=暗流的视觉落地, type=B`，`dependencies=[G-001]`；对 `G-002` 发 SHOW（因为它是一个**新**缺口，不违"同一缺口不得重复消解"）。
3. **t3**"暗流就是表面很平静，但看着心里发紧"：按 R9 精神记为新信息 → 写 `evidence`/`current_value` 更新，或再新建细化 gap。
4. **净效果**：IF 走路径 A，则 `G-001` 的收敛态**在结构上**关掉了"对同一缺口再 SHOW"；IF 走路径 B，则 SHOW 是发往新缺口，逻辑上自洽。
5. **但**"选 A 还是选 B"没有任何字段或迁移能决定 —— 它落在提案自评的"就地接受 vs 重分类仍是**动作选择问题**"（§6 表 F1-05 行，标 ⚠️部分）。

**④ 判定：PARTIAL**

**⑥ 还缺什么**
1. **缺"用户明确拒绝再选"的声明位**。原始失效点要求的第二个机制形态（"用户已明确拒绝再选"）在 Gap Entity 里**没有字段**。`feedback` 闭集里有 `refused`，但提案 §5 的两条 Phase 1 迁移规则只把 `refused` 用在 `gap.blocking=true`（受阻拍板）上，未覆盖"用户拒绝该**动作形态**（不要再给选项）"。
2. **缺"方向收敛后问题集关闭"的迁移**。§2 六态里有 `CONFIRMED`，但提案未写"`CONFIRMED` ⇒ 该 gap 不得再发 SHOW"这条迁移；若没有它，`CONFIRMED` 只是标签，不产生约束力。原始失效点要的是"闭合问题集"，即一条**禁止迁移**，而不仅是可选状态。

### 1.4 G-01 · 第 5 轮把"作品集"改成"电商站"，P0 级推翻时"局部"不可判定

**① 原始多轮输入**
```
第 1 轮：帮我做一个个人作品集网站
第 2 轮：给潜在雇主看，深色、冷静、专业
第 3 轮：要有项目列表和关于我
第 4 轮（AI）：<已按"作品集"确认页面结构、信息架构、验收标准；已给出初版结构稿>
第 5 轮：我改主意了，其实要做的是电商站，要能上架商品、能下单
第 6 轮（AI）：<走 §6.5C 局部重开>   ← 复现点
```

**② V0.3 下的失败动作链**
1. 第 5 轮含明确修正信号"我改主意了" → §6.5A Explicit Revision：新值覆盖旧值 → 分析这次修改影响哪些下游需求 → §6.5A 第 4 步"**只**把受影响的下游槽位重新设为未确认" → 第 5 步"未受影响的信息继续保留"。
2. §6.5C 例子里同类 P0 变化示范（"其实这不是作品集，是工具型 Web App"）→ 重开页面结构 / 用户行为 / 功能 / 技术需求 / 验收标准。
3. **失效**：§6.5A 第 3 步与 §6.5C 第 1 步都只说"分析影响哪些下游""只重开受影响分支"，**没有影响传播规则**（哪些槽位依赖哪些槽位），也没有"重开到哪一层为止"。P0 被推翻时"局部"既不可证伪也不可验收。
4. **结果**：第 4 轮已产出并被默认接受的初版结构稿效力无规定（作废/保留/部分复用）；作品集阶段的品牌调性、配色、页面节奏被当"未受影响"干净搬进电商站；用户只听到"结构我重排一下，其余不变"。
→ 命中：**判定歧义** + **④静默丢失**（旧调性被沿用）+ **⑤出稿与用户原意冲突**。

**③ 套用 Gap Ledger 后的动作链**
1. **t1–t3**：`G-001 topic=要什么产物=作品集网站`（锚点槽位）→ `CONFIRMED`；`G-003 topic=品牌定位`、`G-007 topic=色彩系统`、`G-009 topic=摄影/视觉调性` 各自 `CONFIRMED`，并在建立时写依赖边：`G-001 → affects → {G-003, G-007, G-009, 页面结构, 验收标准}`。
2. **t5**：`"我改主意了"` = §6.5A 信号词 ⇒ 触发 Revision 判定（提案 §3 表：§6.5 Revision **只读，不修改**判定权，结果写入 gap 图）。
   → `G-001` 迁移 `CONFIRMED → CHALLENGED`；写 `supersedes` 边（新值取代旧值）+ `history` 追加一条 `{t:5, event: challenged}`。
3. **传播（§4）**：按 §4 的"最小能力 = 记录依赖 + 标记下游"，沿 `affected` 闭包**只做标记**：
   `G-003 / G-007 / G-009 → CHALLENGED`（**不是**一律重开，也不是凭 AI 逐项检查"是否受影响"）。
4. **可验收点**：受影响集合 = `G-001.affected` 的传递闭包，**可枚举、可证伪**。执行者不能再把"作品集调性"当"我以为没影响的部分"放过——它要么在闭包里（标 `CHALLENGED`），要么不在（必须说明为何无依赖边）。
5. **出稿（t6）**：`CHALLENGED` 的 gap 在用户侧可见（"以下条目因产物变更待确认：品牌定位 / 色彩 / 视觉调性 / 页面结构 / 验收标准"）。
6. **但值层不动**：§4「边界（Phase 1 不做）」明文：**不判定"新值是否与旧值兼容"、不自动重算下游值（留给 Phase 3）**。于是 `G-009.current_value` 仍是"深色冷静专业 / 作品集调性"，直到 Phase 3 裁决。

**④ 判定：PARTIAL**

**⑥ 还缺什么**
1. **"干净搬进"没有被真正阻断 —— 它被推迟了。** Ledger 解决的是**枚举**（受影响集合可证伪），不是**判定**（旧调性在新产物下是否还成立）。而原始失效点原文是："AI 可以把作品集阶段的品牌调性、配色、页面节奏当作'未受影响'干净地搬到电商站上" —— Phase 1 只把"未受影响"这个判断改成"受影响但未重算"。**照原样出稿时，`CHALLENGED` 的旧值仍会作为 `current_value` 被读走**（因为 Phase 1 规定不重算、也不清空），文案里仍可能写"深色冷静专业"。这是**新增的中间态风险**，见 §3 新问题 N-2。
2. **`affected` 图的填充规则完全缺失。** 提案定义了 `affected` 字段与"闭包"语义，但**没有任何规则要求或保证依赖边被登记**。若 `G-009` 的 `affected` 是空的（因为建立时没人写边），闭包 = ∅，则本案例**退回 V0.3 原状**（"局部"仍是空的）。§4 的标题是"依赖与失效传播"，但内容只给了闭包的定义与限制，没给"图从哪来"。
3. **已产出初版结构稿的效力仍无落点**（与 G-04 同源，见 1.5 ⑥-1）。

### 1.5 G-04 · 出稿后推翻 P0 产物：已产出稿的效力无判定

**① 原始多轮输入**
```
第 1～6 轮：<确认了单页海报：尺寸、文案、发布渠道>
第 7 轮（AI）：<已按确认信息出稿，交付 1 张单页海报>
第 8 轮：这个不对，我要的其实是 H5 长页，能在手机上滑着看那种
第 9 轮（AI）：<走 §6.5C 局部重开：重开页面结构 / 布局 / 交互 / 输出格式>   ← 复现点
```

**② V0.3 下的失败动作链**
1. §6.5C 明确覆盖"出稿后用户补充新的关键信息"这一入口 → 判断影响哪些已确认需求 → 只重开受影响分支 → 第 4 步"**不从头重新采访**" → 第 5 步"受影响段落重写，其余不动"。
2. 第 8 轮是 P0 级变化（静态单页 → H5 长页），按 §6.5C 例子重开页面结构 / 布局 / 交互 / 输出格式。
3. **失效**：规则里**没有"已产出稿的效力"判定**。第 7 轮那张海报是作废重做，还是当作素材复用？两种解释对应不同工作量与不同成品。
4. §6.5C 第 4 步"不从头重新采访"与第 8 轮实际冲突 —— P0 产物被推翻时（尺寸、版式、发布渠道、验收标准全要重来），"采访是否重走"本身是待定项，却被规则**预先锁定**为"不从头"。
5. 结果：用户拿到 H5 长页，里面装着为单页海报设计的文案结构与视觉节奏；或者被拉回来重问第 2～3 轮已答过的受众/调性（撞 §6.4）。
→ 命中：**无状态位** + **⑤出稿与用户原意冲突** + **③重复提问**。

**③ 套用 Gap Ledger 后的动作链**
1. **t1–t6**：`G-001 topic=要什么产物=单页海报`（锚点）→ `CONFIRMED`；下游 `G-004 页面结构 / G-005 布局 / G-006 输出格式 / G-008 发布渠道 / G-010 验收标准` 均 `CONFIRMED`，全部登记 `dependencies=[G-001]`。
2. **t7 出稿**：产物 = 第 7 轮海报。在模型内**没有独立的产物对象**，产物只作为若干 `CONFIRMED` gap 的 `current_value` 组合而存在。
3. **t8**"这个不对，我要的其实是 H5 长页"（含"其实不是…是…"式的旧值明确否定）→ §6.5A 信号命中：
   - `G-001` 迁移 `CONFIRMED → CHALLENGED`，`supersedes` 记录新产物规格。
   - §4 传播：`G-001.affected` 闭包内全部 `CONFIRMED → CHALLENGED` —— 这正是"旧稿哪些段落作废"的**可枚举清单**（页面结构 / 布局 / 输出格式 / 验收标准；`发布渠道` 若不在闭包内则保持 `CONFIRMED`）。
4. **t9 动作**：由于 `affected` 闭包恰好覆盖了 P0 相关全部槽位，第 9 轮**不再是"局部重开"**，而是"P0 闭包整体 `CHALLENGED`"——V0.3 中"局部 vs 全量"的自由裁量被闭包遍历替代。
5. **旧稿效力**：`CHALLENGED` 的清单本身就是"这些段落的主人已经不是当前有效值"，用户侧可声明"下面这些沿用旧的"。

**④ 判定：PARTIAL**

**⑤ 为什么不是 SOLVED（诚实说明）**
本条最接近 SOLVED，我仍判 PARTIAL，理由是**判据必须落在"具体状态位"上**：
- 我能指名的状态位是 `CHALLENGED` + `affected` 闭包，它确实消灭了"局部边界不可判定"这一半（可枚举、可证伪，见 1.4 ③）。
- 但**产物级效力**（作废 / 可复用为素材 / 待复核）所需的字段，在提案 §1 的 Gap Entity 字段集中**不存在**。该状态位只在 §4 的**设计意图叙述**里出现过一次（"gap 的 CHALLENGED 直接标注'旧稿哪些段落作废'"，§6 自评表 G-04 行），**未进入实体定义**。设计意图不等于字段；按本轮口径，我不接受"叙述里提到过"作为状态位依据。
- 且"复用为素材"与"作废重做"是两种不同工作量，靠 `CHALLENGED` 一个布尔式标记区分不出来 → 用户仍可能拿到"H5 长页里装着单页海报的文案结构"。

**⑥ 还缺什么**
1. **产物级状态位缺失**（核心）：需要一个能承载"已产出物效力 = 作废 / 可复用为素材 / 待复核"的位置。提案 §1 无此字段，§4 的叙述无法被引用为规则落点。
2. **"采访全量 vs 受影响分支"仍被 §6.5C 第 4 步预先锁定**。提案 §3 表明确"§6.5 Revision 只读，不修改"，因此"不从头重新采访"这条 V0.3 预设**本轮不会被动到**；G-04 的"该不该重走采访"仍无判定结果，Phase 3 才处理。
3. **闭包依赖 §4 的填充规则**（同 1.4 ⑥-2）。

### 1.6 G-05 · "改回原目标" + 多重变更叠加，无统一当前视图、"最早"指代不明

**① 原始多轮输入**
```
第 3 轮：受众改成同行
第 7 轮：产物改成技术文档站
第 12 轮：算了还是按最早的来吧
第 13 轮（AI）：<判定"最早"指哪一版、哪次改动作废>   ← 复现点
```

**② V0.3 下的失败动作链**
1. 第 3 / 7 轮各自独立走 §6.5A（覆盖 + 第 4 步"只重置受影响下游"）或 §6.5C（局部重开）。
2. 第 12 轮含"还是…" → 落在 §6.5A 信号清单（"还是用…"）→ 判 Revision，新值覆盖旧值、分析影响、重置下游。
3. **失效 a（指代）**："最早的"无可解析对象 —— 是第 1 轮原始目标，还是第 3 轮"受众 = 同行"之后那一版？§6.6 决策记录按"每条关键缺口一行"记离散条目，**没有版本号、没有变更序号、没有"某个值在某一轮之后才生效"的时序**；R10 让"留痕"成立，但**留痕 ≠ 可回溯到某一时刻的完整需求状态**。
4. **失效 b（残留）**：第 7 轮已按 §6.5A 第 4 步为"技术文档站"重置一批下游槽位；第 12 轮改回时，需要判定"哪些是第 7 轮带来、现在应消失的"与"哪些是第 3 轮带来、仍有效的"。**两个变更的下游影响集从未被校验是否相交**，因为每次重开都按"当次快照"判，没有跨轮连锁清理 → 改回后残留技术文档站的目录树结构、API 参考页布局。
5. 用户侧：`你说的"最早"是指最初的作品集，还是改成同行受众之后的版本？`——一个用户认为"你比我清楚"的问题；或第 13 轮又问 `这个站主要给谁看？`（第 3 轮已答过）→ 撞 §6.4。
→ 命中：**无状态位** + **判定歧义** + **④静默丢失** + **③重复提问**。

**③ 套用 Gap Ledger 后的动作链**
1. **t3**：`G-002 topic=受众`，`current_value=同行`，`provenance=user_selection` → `CONFIRMED`；`history` 追加。
2. **t7**：`G-001 topic=要什么产物` 由"作品集" → `current_value=技术文档站`，写 `supersedes=<旧值>`，`history` 追加；§4 传播 → `affected` 闭包内下游全部 `CHALLENGED`（解决失效 b 的**可枚举性**：闭包内条目有 `supersedes` 链可回溯来源轮次）。
3. **t12**"算了还是按最早的来吧"：字面命中 §6.5A 信号 → 触发 Revision 判定；`G-001` 需从 "技术文档站" 改回，旧值通过 `supersedes` 链**可以定位到具体条目**。
4. **但"最早的"指哪一版**：Gap Entity 有 `supersedes`（被本 gap 取代的旧 gap）与 `history`（只追加），这构成一条**同 gap 内的值链**；`status=CONFIRMED ∧ confidence=confirmed` 给出**唯一当前值**。
5. **净效果**：第 13 轮"当前有效集合"可回答（这半来自 F4-05 的机制）；残留值有来源链（这半来自 `supersedes`）。
6. **但**把 `"最早的"` 这句自然语言解析成"哪一版"，提案**无任何字段或迁移**可以承载 —— 没有版本号、没有 `version` 字段、`history` 是事件流（`{t, event, by}`）而非可引用版本对象。

**④ 判定：UNSOLVED**（保守判定，理由如下）

**⑥ 还缺什么**
1. **缺"回退指代可解析"**：需要一个能被引用的**版本标识**（或 `history` 里可寻址的状态快照），使"改回到第 N 轮的状态"成为一个确定操作。提案 §1 的 `history` 元素是 `{t, event, by}`（事件），没有"某一轮的完整需求状态"这个概念；§4 只做标记不重算，也不生成快照。**"最早"这一指代在状态模型内不可判定** —— 这是本案例被判 UNSOLVED 的直接原因。
2. **缺"改回"的语义归属**：与 F4-02（改回原值的三种读法）同源，提案 §6 自评表 F4-02 行自认 ⚠️部分（"改回 = Revision 还是撤销仍需 §6.5 层面裁决"）。本轮 §3 表已明写"§6.5 只读、不修改"，故该裁决**不在本轮范围**。
3. **跨轮连锁清理仍未落地**：`supersedes` 让"某个值被谁取代"可查，但**没有**"改回一个上游值时，自动撤销它前一次传播所标记的下游集合"这条迁移 —— 提案 §4 的 Phase 1 边界写明不重算。于是"残留"从"完全看不见"变成"看得见但没人清"，**尚未闭合**。
4. **诚实备注**：本案例的三个失效面里，失效 a（可枚举性/残留可见性）**部分被 Ledger 覆盖**，失效 b（指代）**完全未覆盖**。我按最严的一面判 UNSOLVED；若评审方按"主要症状"判，可下调为 PARTIAL。这个分歧本身记在 §4。

### 1.7 C-01 · 同一维度互斥的模糊词被 Tension 永久挂着

**① 原始多轮输入**
```
第 1 轮：我想做个高端品牌官网
第 2 轮（AI）：这个站主要给谁看？（这决定了整体调性和信息密度）
第 3 轮：给经销商看。视觉上我要高调一点，一眼就有冲击力
第 4 轮：不过整体还是要低调，别太张扬，我们这行不喜欢显摆
第 5 轮（AI）：<继续追问"高调具体指什么">   ← 复现点
```

**② V0.3 下的失败动作链**
1. §3.1 判定顺序："**先按 Tension 试解，解不掉才判 Conflict**"；Tension 一侧列了设计手段清单（信息层级、折叠、渐进披露、分区、分页面、侧栏、hover/详情视图、响应式策略）。
2. "高调 + 低调"被判**可同时满足** → 不进 Conflict 通道 → 不占 §3.1"只提一个最小必要澄清问题" → 不占 §3.2 的 unresolved（§2.5 生效方式行：unresolved 只统计 ASK 通道）→ §6.6 里只能躺"待决定"。
3. Tension 四条处理：不打断采访 / 两条都保留 / 留到设计阶段解决 / 不强迫二选一。
4. **失效**："解不掉"这半步**没有出口条件**：谁来判、判几次、什么时限全缺；R9 的三种触发（用户补充信息 / INSPECT 读到新事实 / TEACH 后表态）**不含"同一维度又来一条反向要求"** ⇒ Tension 一旦成立是终局状态，无再次评估点。
5. 于是 AI 只能反复换措辞追问同一组，撞 §6.4 的"换一种措辞追问同一个点"而无法被制止（§6.4 管的"同一个点"在系统里被记成"两个不同维度的要求"）。
6. 出稿时若设计阶段未真正兼容：既不在「待确认假设」区（§3.1 没让 Tension 进那里），也没标"暂不做"（R12 只覆盖被降为备注的 Type C）→ 靠 §8"不确定就留空并标注"以**合法的静默丢失**收场。
→ 命中：**③无限重复提问** + **④静默丢失** + **⑤出稿冲突** + 判定歧义。

**③ 套用 Gap Ledger 后的动作链**（诚实推演，含失败）
1. **可建账的走法**：建 `G-003 topic=视觉调性, type=A, evidence="高调一点"` 与 `G-004 topic=视觉调性, type=A, evidence="低调别张扬"`，二者 `affected` 相交。
2. **t4 新反向要求**：按"用户新信息"触发重新评估 → `G-003 / G-004 → CHALLENGED`。这一步确实让"同一维度反向要求"有了**再次评估触发点**（补上了 R9 缺的第四种触发）—— 这是 Ledger 的真实增量。
3. **但核心判定仍未解决**：**"张力解不掉"本身不可判定**。§3.1 的可用手段是**开放式工具箱**（"信息层级…响应式策略**等**"），任何"我尽力了"都可以被声称；Ledger 没有、也不打算提供"何时算解不掉"的判据。
4. **更根本的问**：张力组**是不是一个 gap？** 若它不是一个 gap，则它没有 `status`、没有 `attempts`、没有 `feedback_count`，本案要求的三样东西（存活轮次 / 到期升级 / 显式终态）**一个都挂不上**。
5. 提案 §6 自评表把 C-01/C-02 明确列为 **❌ 不解决**（"属 §3.1 Tension/Conflict 判定，非账本问题"），与本推演一致。
6. 提案 §5 反馈账**没有** `TENSION_UNRESOLVED` 这类取值；`feedback` 闭集是 `none | accepted | selected | no_signal | evaded | unable | refused | disagreed | revised` —— 全是**用户反应**的分类，没有一个是**AI 自身判定结果**的分类。这就是张力组无处挂账的字段级原因。

**④ 判定：UNSOLVED**

**⑥ 还缺什么**
1. **缺张力组的对象化**：必须先回答"张力组是不是一个 gap 实体"。若是，需要补 `kind=tension_group` 与存活/轮次字段；若不是，账本对 C-01 零作用。
2. **缺"解不掉"的可判定判据**：需要一个把"设计手段可兼容"从开放式工具箱变成可闭合判定的入口（C-02 里这个需求表现为"呈现方式可兼容"与"资源/代价不可兼容"两类张力的区分）。
3. **缺 AI 侧判定结果的字段**：`feedback` 闭集只装用户反应；"AI 判定本张力无解"这一状态在模型里**没有任何取值可以写**。

### 1.8 C-05 · 冲突组"暂停"后无计数器与终态，只能靠留空静默收场

**① 原始多轮输入**
```
第 2 轮：页面必须支持中文，只做中文
第 6 轮：加英文版，海外也要看
第 7 轮：中文版也要留着啊
第 8 轮（AI）：<判 §6.5B Conflict → 暂停该组 → 只提一个最小澄清问题>
第 9 轮：<回答的是另一个问题：字体和配色>   ← 复现点
第 10 轮（AI）：<继续推进其他维度，冲突组留在暂停态>
```

**② V0.3 下的失败动作链**
1. 第 6 轮"加英文版"= 未声明修正的新要求 → §6.5B → 转 §3.1 Conflict，**不得自动覆盖旧值**。
2. 第 7 轮"中文版也要留"与第 6 轮可同时成立（§6.5 兼容更新）→ 直接采纳。真正的冲突退化成"第 2 轮**只做**中文" vs 第 6 轮"要英文"的旧值 vs 新值互斥。
3. §3.1 四步处理：冲突组**暂停**、不写入需求区；优先于其他普通缺口；只提一个最小澄清问题；澄清后回正常采访。
4. 第 9 轮用户答了别的维度 → 该澄清被回避。
5. **失效**：§3.1 的"暂停"**没有对应记录位** —— 暂停多久、被回避几次、何时必须收口全部无规定。它**不计入 §3.2 的 unresolved**（§2.5 末段：unresolved 只统计 ASK 通道；冲突组走的是 §3.1"冲突组暂停"路径，不是 §3.2「关键槽位」）⇒ **不存在"连续 2 次未澄清 → 默认值 / 部分稿"的出口**。
6. 结果是冲突组既能无限期挂着，又会最终被 §8「需求区只写已确认信息；不确定就留空并标注」**合法清空** —— 用户给过三个版本的说法（只中文 / 加英文 / 中文也要留），最终稿这一维度**空白**，且不算违规。
→ 命中：**无状态位（无计数器、无终态）** + **④静默丢失** + **③重复提问**。

**③ 套用 Gap Ledger 后的动作链**（诚实推演，含失败）
1. **t2**：`G-011 topic=语言版本, type=D, evidence="只做中文"` → `OPEN → CONFIRMED`（用户原话直接给出，§2 表：OPEN 可"可直接确认"），`confidence=confirmed`。
2. **t6**"加英文版"= §6.5B 路径（无信号词、与旧值无法同时成立）→ 提案 §3 表规定：Revision **结果**写入 gap 图（产生 `supersedes` 边 + 下游标记 `CHALLENGED`），但 §6.5B 的**Conflict 分支**没有对应的 gap 迁移语句。
3. **最接近的落点**：`G-011` 迁到 `CHALLENGED`，新建 `G-012 topic=语言版本, evidence="加英文版"`。这至少让两个互斥说法**同时可见**（相对 V0.3 的进步）。
4. **但"暂停"这一步**：§3.1 第 1 条动作是"该冲突组**暂停**"。Gap 六态（OPEN / PROPOSED / CONFIRMED / CHALLENGED / INVALIDATED / CLOSED）**没有"暂停"**：
   - `PROPOSED` 的定义是"**已发出消解动作**，等反馈"（§2 表）—— 它绑定的是**动作已发**，且其语义是"等用户回答一个已提出的问题"，不是"这组先搁着"。
   - `CHALLENGED` 的定义是"**值受质疑**，待重新评估"—— 它表达"值可疑"，**不携带"已向用户提了澄清问题、用户回避了几次"这层信息**。
5. **t9 用户答了别的维度**：`G-011` 的 `attempts` **不自增**（本轮未对该组发动作）；`feedback_count` **不记录**（用户的回答是对**另一维度**的反馈，按 gap 级记账它属于别的 gap）。
6. **t10 及以后**：`G-011` 可以一直停在 `CHALLENGED`。提案 §2 规定 `CHALLENGED` 的出口只有 `VALID`（恢复 CONFIRMED）或 `INVALIDATED`（→ 重新 OPEN）—— **没有"到期"这个迁移**。
7. **终局**：出口按 §3 约束 3 只渲染 `confidence ∈ {assumed, partial}` 的 gap。本案三个说法都来自用户，`confidence` 应为 `confirmed`/`partial`，而冲突未裁决 → 执行者仍可走 §8"不确定就留空" → **合法清空**，与 V0.3 结果一致。
8. 提案 §6 自评表把 C-05 列为 ✅（理由："冲突组即 gap，`feedback=disagreed` 有计数与终态"）—— **本重跑与自评不一致**：§1 的 Gap Entity **根本没有"冲突组"这个 kind**，也没有任何字段承载"被暂停"；`feedback=disagreed` 描述的是"**用户不同意**"，而本案是"**用户没回答**"，二者不同。此分歧记入 §3 新问题 N-3 与 §4。

**④ 判定：UNSOLVED**

**⑥ 还缺什么**
1. **缺"暂停"的状态映射**（直接原因）：§3.1 第 1 条的"冲突组暂停"必须能映射到 `status` 的某个取值（或新增一个 `SUSPENDED` 语义位），否则冲突组在悬置期**不入账**，§8 的"留空"仍能合法清空它。
2. **缺冲突组的独立计数器**：需要"被回避次数 / 已暂停轮次数 / 到期时刻"，且必须**独立于 §3.2 的 ASK 计数**（原文明确要求）。
3. **缺冲突组的显式终态集合**：用户拍板 / 进待确认假设 / 标暂不做 —— 使"不写入需求区"不再等价于"最后静默消失"。
4. **缺 `disagreed` 的适用边界**：`feedback=disagreed` 不能替代"用户回避"；本案第 9 轮的取值应是 `evaded`（用户答了别的维度），而 Phase 1 的两条迁移规则只消费 `no_signal` 与 `refused`，`evaded` 无迁移路径（同 §3 新问题 N-1）。

### 1.9 F4-01 · 同一维度连续 3 次 Revision 后说不出"现在生效哪一版"

**① 原始多轮输入**
```
第 2 轮：做一个高级官网
第 5 轮：视觉方向我改主意了，改成极简
第 7 轮：又想了想，还是改成材质感那种
第 9 轮：视觉这块再改一次，要暗场、单主体、拒绝装饰
第 10 轮：先停一下，现在视觉到底按哪个做？
```

**② V0.3 下的失败动作链**
1. 第 5 / 7 / 9 轮三次命中 §6.5A Explicit Revision（"我改主意了 / 还是…"）→ 每轮"新值覆盖旧值"（第 1 步）、"分析受影响下游"（第 3 步）、"只把受影响的下游槽位重新设为未确认"（第 4 步）。**每轮都自洽。**
2. 到第 10 轮，用户要的是一个**当前值**答案，而 V0.3 手里只有三次独立的"覆盖"操作。
3. §6.6 格式是"每条关键缺口一行" → 同名缺口改三次会产生三行（或一行被覆写、**历史丢失**）；**没有任何规则规定"取时间上最末的一次"**，也没有规定"改到第三次时第一、二次是否已失效"。
4. 契约 R9 只要求"信息变化后重跑决策树"，不产出值视图。
5. 用户听到："你先后说过极简、材质感、暗场单主体，现在是哪一种以你最后一次为准。"——用户问"现在按哪个做"，收到的答案是"以你最后一次为准"，即他自己也不知道的答案。
6. 根因：§6.5A 定义的是**差分操作**，§6.6 定义的是**日志行**，**二者都不是"当前有效集合"**；轮数一多，唯一能回答用户的地方是**对话原文**——而对话正是上下文压缩要丢掉的东西。
→ 命中：**无状态位**（缺"当前值"）。

**③ 套用 Gap Ledger 后的动作链**
1. **t2**：`G-005 topic=视觉方向, type=B, evidence="高级"` → SHOW → 用户确认 → `status=CONFIRMED, current_value=<某方向>, confidence=confirmed, provenance=user_selection`，`history` 追加。
2. **t5**：`"我改主意了"` → `G-005` 迁移 `CONFIRMED → CHALLENGED`（§2 表："新信息、Revision、上游 INVALIDATED"是 CHALLENGED 的入口）；按 §4 标记下游；随后 `"改成极简"` 给出新值 → 评估 → `CHALLENGED → VALID`（值仍成立则恢复）或落新值 → 回到 `CONFIRMED`。**写 `current_value=极简`，旧值只留在 `history`（只追加，不改写）**。
3. **t7**：同一条链再走一遍 → `current_value=材质感`；`history` 追加 `{t:7, event: revised}`。
4. **t9**：第三次 → `current_value=暗场、单主体、拒绝装饰`；`supersedes` 指向第 7 轮的值；`history` 三条俱全（这就是 V0.3 想要而没有的"变更历史"）。
5. **t10 取值**：读 `G-005.current_value` → **一次取值**，不是一次复述。
6. **净效果**：Gap Entity 里 `current_value` 是**单值字段**（§1 定义：`current_value: — # 「现在生效的值」——V0.3 缺失的语义`）⇒ "同时存在三个生效值"在结构上**不可表示**。

**④ 判定：SOLVED**

**⑤ 关键状态位（为什么旧失效不可能发生）**
- 使旧失效不可能的，是 **`current_value` 这个唯一槽位 + `history` 的"只追加不改写"约束**这一对：值层**只能有一个当前值**，历史层**只能追加**。
- V0.3 的失败不是"规则写得不够好"，而是**语义位缺失**：§6.5A 是"覆盖"这个**动词**（`新值 覆盖 旧值`），§6.6 是**日志行**（`事项/类型/动作/状态/依据/结果`，其中 `状态` 是五状态枚举，**不含"当前值"**）。两处都没有一个字段承担"当前生效的值是什么"。原文的结论正是"§6.5A 定义的是**差分操作**，§6.6 定义的是**日志行**，二者都不是'当前有效集合'"。
- Ledger 把"当前值"从**推断**变成**字段**（`current_value` + `provenance` + `confidence`）：第 10 轮的问题从"复述三次修改"（依赖对话原文）变成"读一个字段"（不依赖对话）。**这正是原文要求的"需要一个每维度唯一当前值槽位"**——提案 §1 逐字提供了它。
- 可证伪性：若把 `current_value` 从实体中删掉，第 10 轮立刻退回 V0.3 症状（只能说"以最后一次为准"）。这说明它不是"流程更合理"，而是**该状态位在承担全部修复**。

### 1.10 F4-05 · 20 轮后问"现在哪些还生效"

**① 原始多轮输入**
```
第 1–20 轮：依次给出并修改过 9 项内容——产物（作品集 → 电商站）、受众（HR → 甲方 → HR）、
            主色（蓝 → 绿 → 蓝）、平台（桌面 → 手机）、篇幅（长 → 短）、
            风格（高级 → 极简 → 材质感）、语言（中文 → 中英 → 中文）、
            支付（要不要接入 → 先不接）、合规提示（原来没提 → 加了）
第 20 轮：先别往下写了。现在哪些还生效？给我一份清单，我要拿去跟合伙人确认
```

**② V0.3 下的失败动作链**
1. 每轮修改按 §6.5A 处理，长期维护一份 §6.6 决策记录。
2. 第 20 轮用户要的是"仍然有效"的**过滤视图**。V0.3 能拿出来的只有两样：
   - ① §6.6 逐缺口日志行（`事项/类型/动作/状态/依据/结果`）—— 按"关键缺口"分块，同名缺口多次修改后**出现多行**，**没有"当前值"字段，也没有"被后续覆盖"标记**；
   - ② §8 出口的「待确认假设」区 —— 只装**未确认项**，混着历轮 AI 建议、沉默默认、历史待决定项，**没有时间戳、没有优先级、没有"这条已被后续修改作废"的标记**。
3. 契约 R10 只要求"每个被处理的关键缺口都要留痕"——**留痕 ≠ 有效**。
4. 附加失效：用户这个请求**本身还落不进五动作体系**（既不是 ASK / SHOW / INSPECT / TEACH，也不是 DISCOVER），规则里没有"对既有需求做一致性盘点"这一动作。
5. 用户拿到："把 9 行日志逐条念一遍"+"以上按你的修改顺序记的，具体以哪条为准我再跟你确认"——他要的是能给合伙人确认的清单。
→ 命中：**无状态位（无有效性视图）** + **④静默丢失** + 动作体系无对应动作。

**③ 套用 Gap Ledger 后的动作链**
1. **t1–t19**：9 项内容各建一个 gap（`G-001 … G-009`），每次修改按 1.9 ③ 的链路迁移；`current_value` 始终单值（"蓝 → 绿 → 蓝"结束时 `current_value=蓝`，`history` 三条）。
2. **t20**「现在哪些还生效？」→ 按提案 §2 的关键定义直接求集合：
   ```
   生效集合 = { g ∈ Ledger | g.status = CONFIRMED ∧ g.confidence = confirmed }
   ```
   这正是提案 §2 原文给出的答案形式："用户问'现在哪些还生效'时，答案 = **`status=CONFIRMED and confidence=confirmed` 的集合**，而不再是'逐条回答选了什么'"。
3. **逐项落点**（9 项各自的 `confidence`）：
   - 产物 / 受众 / 主色 / 语言 = 用户改过但均由用户自己拍板 → `confidence=confirmed`；
   - 支付（"先不接"）、合规提示（后加的）= 用户原话给出 → `confirmed`；
   - 若某项是 §6.3 授权默认填的 → `provenance=ai_inference, confidence=assumed` → **不进生效集合，进「待确认假设」**。
4. **动作归属**：该请求不再需要新动作（提案 §6 自评表明确 F4-05 判 ✅；本轮 §7 硬约束也禁止新增动作）。它是对账本的**只读谓词查询**，落在 §3 一致性约束第 3 条的出口渲染侧。
5. **与 §6.6 的关系**：决策记录降级为"快照/审计痕"（§3 表），**推理读 gap，复盘读决策记录**——所以"念日志"不再是与"给清单"竞争的回答路径。

**④ 判定：SOLVED**

**⑤ 关键状态位（为什么旧失效不可能发生）**
- 承担全部修复的是**两个枚举字段的合取**：`status` 与 `confidence`。它们是**gap 对象的属性**，因此"哪些还生效"是一个**定义在账本上的谓词**，而不是一句需要执行者临场判断的话。
- V0.3 的失败根因是**没有任何对象持有"有效性"**：§6.6 的 `状态` 五值（`用户已确认 / 证据已核实 / AI 建议 / 待决定 / 暂不做`）里，"用户已确认"是**动作结果**，不是"在经历了 3 次 Revision 之后**此刻**是否成立"；且决策记录**按缺口分块、同名多行**，天然无法回答集合问题。R10 的"留痕"只保证**存在记录**，不保证**记录有效**——原文的"留痕 ≠ 有效"正是指这一点。
- 关键区分（提案 §2 明文）：`CLOSED ≠ 需求已稳定`，它由 `confidence` 分成 `confirmed | assumed | partial`。**这个区分是 V0.3 完全没有的语义**：V0.3 只有"是否留痕"，Ledger 有"是否成立"。
- 可证伪性：若删掉 `confidence` 字段、只留 `status`，则授权默认填入的项会与用户确认的项一起被判"生效"，第 20 轮的清单立刻**错误**——说明 `confidence` 这个状态位在承担实质判定，而非流程装饰。

**净结论**：Gap Ledger 的修复力**集中在两个字段上** —— `current_value`（值层唯一性）与 `status × confidence`（有效性谓词）。凡失效点是"**某个语义位不存在**"的（F1-02 的计数归属、F4-01 的当前值、F4-05 的有效集合），Ledger **确实**让旧失效在结构上不可能发生；凡失效点依赖"**判定本身不可判定**"（C-01 的"解不掉"、C-05 的"暂停"未对象化）或"**自然语言指代**"（G-05 的"最早"）的，Ledger 只让问题从"看不见"变成"看得见"，**未闭合**。

## 3. 发现的新问题（Ledger 引入或未覆盖的）

> 只记录，不给修法措辞（本轮硬约束：不新增动作、不新增 Type、不写 SKILL 规则）。

### 组 A：字段集与提案自身的叙述不一致（**Ledger 引入**）

**N-1 · "已产出物效力"状态位在字段集中不存在，却出现在设计意图与自评表里**
- 证据：§1 Gap Entity 字段集为 `gap_id / topic / kind / type / source / evidence / blocking / status / resolution / current_value / provenance / confidence / dependencies / affected / supersedes / attempts / last_resolution / feedback / feedback_count / history` —— **无产物效力字段**。
- 但 §6 自评表 G-04 行判 ✅ 的依据是"gap 的 `CHALLENGED` 直接标注'旧稿哪些段落作废'"；§4 标题表述为"Validity Layer"。
- 影响：G-01、G-04 两例的判定**不能**引述该状态位；设计意图被误读为已实现的字段。
- 风险等级：**高**（直接影响两例判定，且是"设计文档内部不一致"，不是规则缺失）。

**N-2 · `CHALLENGED` 的"值与动作"对称性缺口 —— 会产生新的中间态错误出稿风险**
- 证据：§2 表给出 `CHALLENGED → VALID / INVALIDATED` 两个出口，但**未规定 `CHALLENGED` 期间的值是否可被出稿读取**；§4 边界明文"不自动重算下游值"，即 `current_value` 保持旧值不变。
- 推演：若出稿发生在"`CHALLENGED` 未闭合"时（G-01/G-04 的第 6/9 轮正是这样），执行者读 `current_value` 会拿到**已被质疑但仍标注为当前值**的旧值 → 与 V0.3 的"干净搬进"症状**同形**，只是多了个标记。
- 对比 V0.3：V0.3 的问题是"没标记所以搬过去了"；Ledger 若不允许"禁止读取 CHALLENGED 值"，问题变成"有标记但仍搬过去了"。**这是新增风险，不是继承风险。**

**N-3 · `feedback=disagreed` 被用来承担"冲突组有终态"，但它描述的是另一种情形**
- 证据：§6 自评表 C-05 行："冲突组即 gap，`feedback=disagreed` 有计数与终态"。
- 反证：C-05 第 9 轮的情形是"用户**回避**了澄清问题（答了别的维度）"，不是"用户**不同意**"。提案 §5 闭集里对应的取值应是 `evaded`。
- 影响：自评把一个语义不同、且**无迁移规则消费**的字段当作已覆盖的证据。

### 组 B：提案已声明"不做"但案例仍然依赖的能力（**未覆盖**，需评审确认是否接受）

**N-4 · `affected` 依赖图没有填充规则 —— 闭包可能为空**
- 证据：§4 定义 `affected` 为"本缺口的值一旦变化，会影响哪些下游"，并规定"局部 = `affected` 闭包（含传递闭包）"；但全文**没有**任何一句要求"建立 gap 时必须登记依赖边"，也没有"图从哪来"的来源规定。
- 影响：G-01 与 G-04 的修复**完全**依赖图已被填充。空图 ⇒ 闭包 = ∅ ⇒ 退回 V0.3 原状。**这是本组最实际的单点故障。**

**N-5 · `feedback` 闭集有 9 个取值，Phase 1 迁移规则只消费 2 个 —— `evaded` 是一条死路**
- 证据：§5 闭集 `none | accepted | selected | no_signal | evaded | unable | refused | disagreed | revised`；两条 Phase 1 迁移规则只用到 `no_signal` 与 `refused`。
- 影响：`evaded`（明显回避）在 §3.2 里是**明确计入 unresolved 的四种形态之一**，Ledger 把它收进闭集后**不给任何迁移**，于是"记账了但不能推进"——比 V0.3 的"根本没记"更隐蔽。F1-04、C-05 都踩这里。

**N-6 · `attempts` 与 `feedback_count` 是两个计数器，提案未规定二者的换算法**
- 证据：§5 写入时机表：`attempts` 每次发动作 +1；`feedback_count` 收到反应时累加。F1-02 中"嗯"（无动作轮）只加后者。
- 影响：§5 迁移规则 1 的前件写作 `last_resolution=shown ∧ feedback=no_signal ∧ attempts≥2`。若把上限挂在 `attempts` 上，F1-02 在 t4 时 `attempts` 仍为 1，**闸门不复位**；若挂在"连续无有效反馈的轮数"上，则该计数在提案里**没有字段名**。F1-02 判 SOLVED 建立在前者被正确解释为"连续无法获得有效反馈"的前提下（§2 PROPOSED → CLOSED(assumed) 行的措辞），此处存在实现口径分歧。

### 组 C：与本轮范围无关但重跑暴露的既有空白（**继承**，非 Ledger 引入）

**N-7 · 六态中没有"暂停/悬置"语义，而 §3.1 的主要动作恰恰是"暂停"**
- 证据：六态 = `OPEN / PROPOSED / CONFIRMED / CHALLENGED / INVALIDATED / CLOSED`；§3.1 第 1 条动作 = "该冲突组**暂停**"。最接近的 `PROPOSED` 定义是"**已发出消解动作**，等反馈"，`CHALLENGED` 定义是"值受质疑"，两者都不承载"提了澄清但被回避了几次"。
- 影响：C-05 判 UNSOLVED 的直接原因。

**N-8 · `feedback` 闭集全是"用户反应"的分类，没有"AI 自身判定结果"的分类**
- 证据：9 个取值逐一看：`none`（无）/ `accepted` / `selected` / `no_signal` / `evaded` / `unable` / `refused` / `disagreed` / `revised` —— 全部描述用户侧状态。
- 影响：C-01 要求"张力组到期仍无法给出可判定结果 ⇒ 升级为用户拍板"，这个"**AI 判定无解**"的事件在模型里**没有任何取值可以写**。这也是 §5 被定位为"与 Phase 2 的接口"的必然结果，但重跑证明它不只影响 Phase 2 的细腻度，而是**直接卡住 C-01 的判定**。

**N-9 · `history` 是事件流而非可寻址版本，无法支撑"改回到某一版"**
- 证据：§1 `history` 元素 = `{t, event, by, detail?}`（如 `{t:1, event:created, by:user_statement}`）。
- 影响：G-05 的"最早的"指代不可解析；F4-02（改回原值）的三种读法在 `supersedes` 链上仍不可裁决。自评表对此判 ⚠️部分，与重跑一致。

**N-10 · 提案引用的独立复核文件 `gap-ledger-coverage.md` 在仓库中不存在**
- 证据：§6 开头写"完整逐点对照见 [gap-ledger-coverage.md](gap-ledger-coverage.md)（独立复核）"，并声明"以复核为准"。
- 现状：`docs/v04/` 下无该文件（`Get-ChildItem` 与 glob 均未见）。
- 影响：本轮重跑**无法与复核结论对表**；本文件中的 §2 差异表是**首次**提出的分歧，尚待独立复核确认。
